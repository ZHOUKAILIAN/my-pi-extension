## 产品职责

Workflow Governance Runtime 将 Feature、Fix 等任务作为受控工作流运行。它通过工具白名单、状态校验、Artifact schema 和审计记录控制任务拆分、角色、上下文、能力、状态推进与最终完成；不能只依靠 prompt。

Runtime 提供通用治理骨架；Skill 提供方法，Project Knowledge 提供项目语境，各 Workflow Extension 提供入口特有流程与验收。

整个项目的交互和设计必须降低人的认知成本。用户主路径使用业务语言、清晰摘要、少量明确选项和渐进式详情，不要求用户理解 Stage、Node、Artifact、`runId`、版本绑定或 Guard；这些技术事实仍完整保留在详情、审计和调试入口。简化交互不能降低 Runtime 校验、Guard、版本绑定或 Acceptance 控制；无 UI 场景提供等价的结构化接口。

## 对象关系

```text
Workflow Extension
└── Workflow Definition（静态规则）
    ├── Node Definitions
    │   └── Node Definition
    │       ├── Task：要完成什么
    │       ├── Policy / Worker Profile：谁来做、允许怎样做
    │       ├── Context Capsule：可以看到什么
    │       └── Artifact Contract：必须提交什么
    ├── Stage / Transitions
    ├── Transition Guards
    └── Acceptance Definition

Workflow Run（一次运行）
├── 当前 Stage / 基准版本 / 工作目录
├── Node Executions
├── accepted Artifacts
├── Guard / Transition Records
├── Checkpoints
└── Acceptance Result

Node Execution
└── Worker Session / attempts → Worker Artifact
```

## 强制执行流

```text
Run + Node Definition
→ Runtime 解析 Task / Policy / Profile / Capsule
→ Worker Session
→ Worker Artifact
→ 合同校验
→ Controller + Transition Guard
→ 下一 Node / 重试 / 等待用户 / BLOCKED / ACCEPTED
```

- Artifact 合法不等于 Stage 自动推进。
- 只有 Controller 可以改变 Run 状态。
- Guard 只决定单次迁移；Acceptance Definition 决定整个 Run 能否进入 `ACCEPTED`。
- `blocked` 不是通过。

## 不可混淆

```text
Workflow Definition   一类任务的静态规则
Workflow Run          该规则的一次运行
Stage                 Run 当前在哪里
Node Definition       要执行什么工作
Node Execution        Node 在某次 Run 中的一次调用
Worker Session        执行该调用的代理会话
Artifact              Run 接受的结构化事实材料
Policy                约束当前执行
Transition Guard      当前一步能否推进
Acceptance Definition 整个 Run 能否完成
```

## Worker 与上下文

- 一个 Worker Session 只承担一个 Node，不跨 Node 工作，不得再委派 Worker。
- Worker 只能使用当前 Policy 允许的工具、Skill 和上下文。
- Context Capsule 是最小、版本化输入；默认不含主 Agent 完整历史。
- 后续 Worker 通过 Artifact 获取上游事实，不复制完整对话。
- Workflow 执行期间，原对话可以展示当前活跃 Worker，并把用户自然语言补充先持久化、再原子绑定到提交时的 Run/Worker；同一 Run 后续 Worker默认按版本引用获得补充。
- Node 使用严格 close fence：fence 前输入必须由当前 Worker 消费并以最新补充版本重新交付 Artifact 后才能迁移；fence 后提交失败并保留输入，用户确认新接收者后重新提交，不得静默丢失、广播或改投。
- 用户可在原对话通过当前 subagent 的模型选择器切换当前活跃 Worker 的模型；项目 Node 模型是默认值，候选必须属于 Pi scoped/available 已认证范围并满足当前 Worker 兼容约束，且不修改主 Session、后续 Node、项目默认 Policy或能力边界。
- 用户补充信息不是 User Decision Artifact；自然语言中的接受、拒绝、暂停或完成措辞不能直接推进 Stage、通过 Guard 或形成最终验收。
- Skill Routing 和 Role prompt 不是安全边界；只有文件系统、网络和实际能力隔离可构成安全边界。

## Artifact

Artifact 是 Workflow Run 接受的结构化事实材料，包括 Worker、User Decision 和 Controller Artifact。它必须带类型/schema、`producerKind`、生产者身份、所属 Run、来源版本和可追溯引用；Worker Artifact 还要关联 Node Execution/Worker，并通过 Node 的 Artifact Contract。Guard/Transition Record 与 Acceptance Result 是独立控制记录，Worker 不能伪造。适用时记录检查范围、证据、已验证边界、未验证项、风险与结论。

## 正式方案评审

任何入口产生或改变正式需求方案、技术方案、架构决策或验收标准时，在进入实现或成为正式依据前必须经过多个 Agent 独立交叉评审。

评审至少覆盖目标一致性、影响面、假设与替代方案、风险与回滚、验收可验证性。至少一个正式 Reviewer 必须与提案者使用不同 `workerId`；变更 Reviewer 必须不同于实现者。进入实现前必须保证评审版本等于采纳版本、必需方案 Finding 已正式关闭、Adoption Decision 引用了接受的 Review。实质修改会使旧采纳失效并触发重审。纯局部实现且不改变正式方案时可不触发完整方案评审。

## Finding 与裁决

Finding 必须绑定固定版本或产物，并包含严重度、位置、证据、影响、建议和 `required`。`required` 必须由版本化 Workflow/Policy 根据严重度与类别决定；实现者不得自行降级。

```text
implementer: fixed_claimed | disagree
reviewer/arbiter: resolved_fixed | resolved_rejected | blocked
```

`fixed_claimed`、`disagree` 和 `blocked` 都不能通过 required Finding Guard；只有关闭者在目标 revision 验证修复后的 `resolved_fixed`，或正式驳回 Finding 本身的 `resolved_rejected` 才满足。Finding 回应者/实现者不能关闭对应 Finding。Arbiter 必须不同于争议涉及的所有提案者、挑战者、实现者、Reviewer、Finding 作者和回应者，不得裁决自己参与的工作。

## Extension

- Feature：建设尚不存在的新产品能力；具体规则见 [Feature 规范](扩展/feature-扩展.md)。
- Fix：调查和处置已有系统问题并验证结果；具体规则见 [Fix 规范](扩展/fix-扩展.md)。
- 两者都可采用轻量路径；是否评审正式方案取决于产物变化，不取决于入口名称。

## 审计

Audit 必须记录实际 Workflow/Node 版本、Stage、Worker、Role、模型及变化、Skill、工具事件、Capsule 引用、用户补充信息的绑定/投递/消费、Artifact、未验证项、Guard 决策、迁移、错误、恢复和 Acceptance Result；“模型说通过”不是充分证据。
