# Workflow Governance Runtime 产品定义

- 状态：`DECIDED`
- 层级：第一层（L1）
- 责任：定义所有 Workflow Extension 共享的产品语义；不描述具体实现机制

## 1. 产品目标

Workflow Governance Runtime 是由 Pi extension 承载的任务治理层。它把 Feature、Fix 等任务组织成受控工作流，负责拆分任务、分配角色、限制上下文与能力、校验产物、控制状态迁移、判断最终完成并记录审计事实。

Runtime 必须通过工具白名单、状态转换校验、Artifact schema 和审计记录实施控制，不能只依靠 prompt 提醒模型遵守流程。

Runtime 只提供通用治理骨架。具体工作方法由 Skill 提供；仓库结构、业务术语和验证命令由 Project Knowledge 提供；各入口的目标、流程和验收语义由对应 Workflow Extension 提供。

## 2. 核心对象

产品对象分为静态规则、运行实例和实际执行三层：

```text
静态规则：Workflow Extension → Workflow Definition → Node Definitions
运行实例：Workflow Run → Node Executions
实际执行：Node Execution → Worker Session → Artifact
```

### 静态定义

```text
Workflow Extension（Feature / Fix）
├── 用户命令
└── Workflow Definition
    ├── Node Definitions
    │   └── Node Definition
    │       ├── Task：要完成什么
    │       ├── Policy / Worker Profile：谁来做、允许怎样做
    │       ├── Context Capsule：可以看到什么
    │       └── Artifact Contract：必须提交什么
    ├── Stage / Transitions
    ├── Transition Guards
    └── Acceptance Definition
```

Workflow Definition 描述一类任务应当怎样运行，不保存任何一次任务的当前状态或执行结果。

### 运行实例

```text
Workflow Run
├── runId、基准版本、工作目录和当前 Stage
├── Node Executions
├── 已接受的 Artifacts
├── Transition / Guard Records
├── Checkpoints
└── Acceptance Result
```

Workflow Run 是 Workflow Definition 的一次实际运行。Node Execution 是该 Run 对某个 Node Definition 的一次调用。

Run 中的可追溯材料按生产者区分：Worker 在 Node Execution 中提交 Worker Artifact；用户决定形成 User Decision Artifact；Controller 生成 Guard/Transition Record 和 Acceptance Result。它们都必须记录生产者类型、身份、所属 Run、来源版本和审计引用，但只有 Worker Artifact 受 Node 的 Artifact Contract 约束。

### 一次 Node 执行

```text
Workflow Run + Node Definition
        ↓ Runtime 解析
Task + Policy + Worker Profile + Context Capsule
        ↓
Worker Session
        ↓
Worker Artifact
        ↓ 合同校验
Controller + Transition Guard
        ↓
下一 Node / 重试 / 等待用户 / BLOCKED / ACCEPTED
```

Artifact 校验通过不代表 Stage 自动推进。只有 Controller 可以依据 Transition Guard 改变 Run 状态；只有整体满足 Acceptance Definition 才能进入 `ACCEPTED`。

## 3. 入口与职责

### Feature

用于建设尚不存在的新产品能力。具体产品流程由 [Feature Extension](扩展/feature-扩展.md) 定义。

### Fix

用于调查和处置已有系统中观察到的现象、异常或维护问题，并验证结果。具体产品流程由 [Fix Extension](扩展/fix-扩展.md) 定义。

Feature 和 Fix 表示任务性质，不表示固定工作量。两者都可以采用轻量路径；是否进入正式方案评审取决于是否产生或改变正式方案，而不是入口名称。

### Workflow Extension

顶层产品入口，拥有用户命令和自己的 Workflow Definition。Core Runtime 不拥有 Feature 或 Fix 的具体 Node、状态路径和业务验收标准。

## 4. 流程概念

### Stage / Transition

Stage 表示 Workflow Run 当前在哪里；Transition 定义可以进入哪些后续 Stage。Stage 不是 Node：一个 Stage 可以执行多个 Node，同一个 Node Definition 也可以因重试、并行提案或独立复核被多次执行。

### Transition Guard

判断某一条 Transition 当前是否允许发生。Guard 可以检查 Artifact、证据、候选版本、Finding、用户决策、预算或审批。单个 Guard 通过只代表当前一步可以推进，不代表整个任务完成。

### Acceptance Definition

Workflow Run 进入 `ACCEPTED` 前必须整体满足的完成条件。它可以综合检查最终候选版本、必要 Artifact、验证证据、未关闭 Finding、未验证项和用户决策。

### Node Definition / Node Execution

Node Definition 是静态工作定义；Node Execution 是它在某个 Workflow Run 中的一次调用。Node 不等同于 Stage、Agent、进程、Workflow Run 或 Pi Extension。

### Worker / Worker Session

Worker 是 Runtime 委派的独立执行代理；Worker Session 是它在某次 Node Execution 中的执行会话。

一个 Worker Session 只承担一个 Node 任务，不能跨 Node 连续工作，也不能再委派其他 Worker。正常执行通常使用一个 Session；有限重试可以产生多个 attempt，并行提案或独立复核可以创建相互独立的 Node Execution。

### Role

Role 是一次委派中的职责与权限，不是模型名称或用户身份。常见 Role 包括 `investigator`、`requirement_proposer`、`architect`、`challenger`、`implementer`、`reviewer`、`verifier` 和 `arbiter`。

## 5. 执行控制

### Policy

Policy 是按 Workflow Run、Stage、Role 和 Node 解析的版本化执行规则，可以约束 Worker Profile、工具与 Skill 白名单、上下文范围、Artifact schema、预算和审批条件。

职责边界如下：

```text
Workflow Definition  定义允许的流程与产品完成条件
Policy               约束当前 Node 怎样执行
Transition Guard     判断本次迁移能否发生
Runtime              执行、校验并审计以上规则
```

### Context Capsule

Runtime 交给单个 Worker 的最小、版本化上下文包，可以包含 Task、Role 指令、允许的 Skill、指定上游 Artifact、验收标准、基准版本和必要文件引用；默认不包含主 Agent 的完整对话历史。

### Skill / Project Knowledge

- Skill 提供工作方法、领域知识、检查标准和输出要求。
- Project Knowledge 提供仓库结构、接口关系、业务术语、运行环境和测试方式。
- 二者都不能改变 Workflow 状态或单独授权阶段完成。
- 它们的要求必须通过 Artifact、证据或验收条件体现为可审计事实。

### Context Isolation / Capability Isolation

Context Isolation 限制 Worker 可以获得的信息，包括资源发现、prompt/Context Capsule、文件系统和网络三个层次。只有文件系统与网络隔离可以作为安全边界。

Capability Isolation 限制 Worker 实际可以执行的动作，例如工具白名单、受限 shell、只读挂载、临时 worktree、容器或受控工具。Role prompt 和 Skill Routing 本身都不构成安全隔离。

## 6. Artifact 与评审

### Artifact

Artifact 是 Workflow Run 接受的结构化事实材料。根据生产者分为：

- Worker Artifact：Worker 在 Node Execution 中提交，必须通过该 Node 的 Artifact Contract；
- User Decision Artifact：记录用户对明确问题作出的选择及其影响；
- Controller Artifact/Record：记录采纳决定、阻塞、报告等确定性控制结果。

Artifact 必须包含类型、schema、`producerKind`、生产者身份、所属 `runId`、来源版本和可追溯引用；Worker Artifact 还必须关联 `nodeExecutionId` 和 `workerId`。适用时应记录检查范围、证据、已验证边界、未验证项、风险和结论。

后续 Worker 应引用上游 Artifact，不应依赖完整历史对话。Skill 决定工作方法，Worker 形成 Worker Artifact，Runtime 负责校验、保存、交接和审计。Guard/Transition Record 与 Acceptance Result 是由 Runtime 持有的独立控制记录，不能由 Worker 伪造。

### 跨入口正式方案评审

任何入口产生或改变正式需求方案、技术方案、架构决策或验收标准时，该产物在进入实现或成为后续正式依据前，必须经过多个 Agent 的独立交叉评审。

评审至少覆盖：目标一致性、影响面、关键假设与替代方案、风险与回滚、验收标准的可验证性。至少一个正式 Reviewer 的 `workerId` 必须不同于提案者；变更 Review 的 Reviewer 必须不同于该候选版本的实现者。

评审结果、修改回应和最终采纳决定都必须形成可追溯 Artifact。进入实现前必须同时满足：采纳版本就是完成评审的版本；全部必需方案 Finding 已正式关闭；Adoption Decision 引用被接受的 Review 集合。影响结论、范围、风险或验收标准的修改会使旧采纳决定失效，必须重新评审；纯编辑修改只有在 Guard 记录可审计 diff 后才可免于重审。

纯局部实现且没有产生或改变正式方案时，不强制升级为完整方案评审。

### Review Finding / Disposition

Review Finding 针对固定版本或产物，至少包含严重度、位置、证据、影响、建议和 `required`。`required` 由版本化 Workflow/Policy 根据严重度与类别确定；实现者不得自行降级，任何调整都必须审计。

| 状态 | 含义 | 是否满足 Guard |
| --- | --- | --- |
| `fixed_claimed` | 实现者声明已在新版本修复，并引用版本和证据 | 否，等待独立复核 |
| `disagree` | 实现者提交反证 | 否，等待 Reviewer 接受或 Arbiter 裁决 |
| `resolved_fixed` | 关闭者已在目标版本验证修复 | 是 |
| `resolved_rejected` | Finding 本身被正式驳回 | 是 |
| `blocked` | 当前无法修复或裁决 | 否；必需 Finding 只能使 Run 等待或进入 `BLOCKED` |

Finding 的回应者或对应变更的实现者不能正式关闭该 Finding。Reviewer 可以在复核证据后关闭；证据冲突交给独立 Arbiter。

### Arbiter

Arbiter 处理达到轮次上限、证据冲突或影响状态推进的争议。其 `workerId` 必须不同于争议涉及的所有提案者、挑战者、实现者、Reviewer、Finding 作者和回应者，不得裁决自己参与的方案、实现、Review 或 Finding。

## 7. Trace 与 Audit

Trace 是面向用户和调试的过程摘要；Audit 是可持久化、可回放的控制记录。

审计应记录实际使用的 Workflow 与 Node 版本、Stage、Worker、Role、模型、Skill、工具事件、Context Capsule 引用、Artifact、未验证项、Guard 决策、状态迁移、错误、恢复动作和 Acceptance Result。只记录“模型认为通过”不构成充分审计。

## 8. 分层边界

本文件与各 Extension 的产品规范属于 L1，回答“产品必须保证什么”。[产品上下文摘要](产品上下文摘要.md)是本层的压缩派生版本，不是 L2。

可执行 Workflow Definition、状态枚举、Policy 合并、Guard 代码、Artifact JSON Schema、Worker 生命周期、存储接口、源码和测试属于 L2，回答“当前怎样实现和验证这些保证”。
