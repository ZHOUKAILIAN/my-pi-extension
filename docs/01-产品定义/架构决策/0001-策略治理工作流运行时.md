# 架构决策 0001：采用策略治理的 Workflow Runtime

- 状态：原型阶段已采纳，并根据 2026-08-18 多模型评审结果修订
- 日期：2026-08-18

## 背景

本项目承载的是一套工作方法，而不是通用的 prompt 集合。它需要控制任务如何进入系统、每个阶段允许哪些角色执行、哪些证据可以在角色之间交接、每个角色可以使用哪些 Skill 和工具，以及任务何时可以推进。

只依赖 prompt 无法强制执行这些约束。Worker 可以忽略角色指令，主 Agent 可以绕过建议流程，不受限制的 Skill 发现还会把无关的操作规程带入当前任务。

以下三种控制必须保持区分：

- Skill Routing 决定角色可以发现和加载哪些 Skill。
- Context Isolation 决定 Worker 可以接收哪些任务材料。
- Capability Isolation 决定 Worker 实际可以读取、写入或执行什么。

## 决策

将本扩展实现为策略治理的 Workflow Runtime。

版本化的 Policy 是每个 Workflow Run 的唯一控制源。它定义阶段、允许的角色、状态迁移、Skill 路由、Context Capsule 构造、工具白名单、Artifact schema、预算、审批要求和写入模式。

扩展负责校验和执行 Policy。主 Agent 可以请求委派，但不能在 Policy 之外自行扩大工具、Skill 集合或 Worker 上下文。所有未列入白名单的工具都必须默认拒绝。

Worker 接收最小化的 Context Capsule，并通过版本化 Artifact 交换信息，而不是不受限制地继承主 Session。Context 要么以 `--no-context-files` 显式注入并严格控制，要么继承所有已加载的 context 文件，并记录其清单和 hash。初始 Worker Runtime 采用子 Pi CLI 进程。Skill 发现通过 `--no-skills` 和显式、固定 hash 的 `--skill` 路径进行限制。Capability Isolation 由独立的工具白名单实现；在需要时，再增加 shell wrapper、worktree、进程策略以及容器/OS sandbox。CLI 参数和 Pi 工具列表只是资源控制，不是安全 sandbox。

Workflow Runtime 只提供通用流程骨架，不拥有具体仓库的调查方法、领域知识或业务验收标准。调查和验证标准由 Skill、项目知识和项目策略提供；Runtime 负责执行这些声明、校验 Artifact、控制状态并记录可审计证据。

## 影响

### 正面影响

- 工作方法可复现、可检查、可审计。
- 多 Agent 方案评审和代码评审可以使用确定性的阶段门禁。
- Skill 使用和上下文交接成为显式数据，而不是不可见的 prompt 行为。
- 后续 Policy 变化可以版本化、评审和回滚。

### 成本与风险

- Policy schema 的设计和校验会成为核心产品工作。
- 一些灵活的一次性行为需要显式扩展 Policy 或请求用户升级决策。
- Pi CLI 的资源控制本身不是安全 sandbox；文件系统和 shell 边界需要单独实现和验证。
- 初始 CLI Worker 协议需要结构化结果校验，并尽早评估 JSON/RPC，以支持工具事件、用量和资源清单。
- Policy、Artifact 和 trace 数据必须放在 Worker 不可写的控制平面中，并为每个 Run 固定 digest。

## 备选方案

### 仅使用 Prompt 编排

不采用。它可以引导模型行为，但不能阻止模型绕过直接工具、加载无关 Skill 或过度共享上下文。

### 在 Extension TypeScript 中硬编码全部 Workflow 规则

不采用。它会把 Policy 变化绑定到代码发布，使不同项目难以复用，并让真实流程规则不易被独立评审。

### 使用外部 Agent Team Runtime 作为控制平面

暂缓。它可能提供有价值的能力，但在让它接管本项目的核心控制平面之前，仍需评估其 Policy、trace、权限和生命周期模型。
