## 2. 每个问题到底意味着什么

### D1：没有 Arbiter

**场景**：一个 Reviewer 认为 Finding 已修复，另一个 Reviewer 认为没有修复，或者实现者对 Finding 提交反证。当前系统有 Review quorum，但没有“争议裁决”这个角色和产物。

**影响**：不是普通流程一定跑不通，而是争议时没有独立、可审计的最终裁决者。若直接让主 Controller 选一个结果，会把裁决权混入编排逻辑。

**边界**：Arbiter 不能等同于再跑一次 Reviewer。它必须不同于提案者、挑战者、实现者、Reviewer、Finding 作者和回应者；Finding 的状态也要支持 `fixed_claimed`、`disagree`、`resolved_fixed`、`resolved_rejected`、`blocked` 等语义。

### D2：报告事实来源与字段不完整

**场景**：用户输入可能很长，Intake Agent 应先把它压缩成可复用的用户可读结果；调查 Agent 再从用户描述、代码和日志中确认“预期行为、实际行为、是否复现、影响范围、时间线和排除的候选原因”。但当前报告直接使用原始 `problem` 参数；同时 `InvestigationArtifact` 只正式要求 `route/rootCause/evidence`，模型即使看到了信息，也没有稳定的合同字段交接给后续报告。

**影响**：原始长文本可能直接进入报告，导致摘要过长、重点不稳定；Intake 对问题的规范化结果没有成为唯一事实来源；报告也无法可靠回答“为什么确认这是问题”“因果链怎样闭合”“哪些可能性已排除”“哪些还没验证”。这主要影响可读性、可追溯性和事后阅读，不改变当前人工验收的控制权。

**推荐的最小 Intake 输出**：保留两个用户可读层次，但不再把原始长文本直接展示。

```ts
interface IntakeArtifact {
  kind: 'intake';
  summary: string;   // 一句话：这是个什么问题
  overview: string;  // 两三句话：场景、影响和当前已知上下文
  environment?: string;
  scope?: string;
  urgency?: 'low' | 'medium' | 'high' | 'critical';
}
```

- 原始 `problem`：保留为 Run 的原始输入/追溯事实，但不直接进入最终报告或人工摘要；
- `summary`：Intake 规范化后的一句话问题摘要，不是原文截取；
- `overview`：有长度上限的两三句话概要，只补充场景、影响和 Intake 已知上下文，不写最终根因、T0-T4 时间线或完整调查结论；
- `environment`/`scope`/`urgency`：继续单独保留为结构化字段，缺失时显示「尚未确认」；
- 现有 `phenomenon`：作为旧 Artifact 兼容字段保留一段迁移期；兼容投影时将 `phenomenon` 作为 `summary` 的降级来源，缺少 `overview` 时显示「尚未确认」；
- 这两个字段是本方案的 L2 设计选择，不是 L1 额外要求；如果最终要把“摘要/概要”提升为产品固定术语，需要另行更新 L1。

**推荐归属**：

- `IntakeArtifact`：`summary`/`overview`、环境、初始范围、紧急度；`summary` 是一句话问题摘要，`overview` 是两三句话的场景/影响概要；
- `InvestigationArtifact`：预期/实际/确认结果、调查后的影响面、分层根因、时间线、排除候选、停止调查理由、证据缺口；
- `DispositionArtifact`：处置类型、最小范围、风险、验证目标、是否需要正式方案；
- `VerificationArtifact`：原始问题、回归/兼容性、执行命令或检查、验证结论、剩余风险、未验证项；
- Review Artifact：保留复核意见和复核发现，不冒充原始调查事实。

### D3：处置等待没有真正进入等待态

当前 `dispositionType` 虽有 `wait_decision`、`external_action`，但 Controller 只有：

```text
insufficient_evidence -> BLOCKED
requiresRepositoryChange=true -> CHANGE_PLAN_REVIEW
requiresRepositoryChange=false -> VERIFYING
```

因此 `wait_decision` 和 `external_action` 会走到 VERIFYING。问题不是多一个枚举，而是“需要谁在什么时候决定什么”没有进入状态机。

**推荐设计**：仍复用 Stage `WAITING_FOR_USER`，但在 Runtime/checkpoint 增加结构化 `pendingDecisionKind`，至少区分：

```text
pre_disposition_decision   处置尚未获用户/外部决定
final_acceptance            自动验证完成后的最终人工验收
```

两者使用不同的可选动作和 Guard。不能用一个“approve”同时表示“同意开始验证”和“同意最终完成”。`external_action` 还需要外部动作已完成的结构化证据，不能仅凭用户点选替代。

### D4：验证缺少条件没有 BLOCKED

当前验证 Artifact 合同错误和业务验证失败都可能表现为 `accepted:false` 或异常。Controller 只区分：通过→等待人工，不通过→回 IMPLEMENTING；合同重试两次后暂停。

**推荐分类**：

| 验证结果 | 含义 | 目标 |
|---|---|---|
| `contract_invalid` | Artifact 缺字段、证据格式错误 | 重试，仍失败则暂停，不冒充 BLOCKED 业务状态 |
| `verification_failed` | 条件可执行，但原问题/回归验证失败 | 回 IMPLEMENTING |
| `verification_blocked` | 缺权限、环境、外部系统或必须的用户动作 | 进入 BLOCKED，记录责任方和解除条件 |
| `verification_passed` | 必检项完成且证据充分 | WAITING_FOR_USER |

实现上可以通过新增结构化 `verificationOutcome`/`blockedReason`，或由 Controller 生成专用 `guard_rejection`；需要避免只看 `accepted:false` 猜测原因。

### D5：正式方案升级没有兑现

L1 明确：如果 Fix 改变正式需求、技术方案、架构决策或验收标准，必须走 Core 的 Proposal→Independent Review→Adoption。当前字段 `requiresFormalPlanReview` 只是声明，没有任何消费点。

**风险**：普通 Change Plan Review 可能被误认为已经完成了正式方案采纳，但它们不是同一件事。`change_plan_review` 评估的是一个 Fix 修改计划，不自动产生正式 Proposal、Review 集合和 Adoption Decision。

**推荐策略**：

1. `requiresFormalPlanReview !== true`：走当前 Fix change plan 流程；
2. `=== true` 且正式流程未实现：进入 BLOCKED 或 WAITING，明确“等待正式方案采纳”，不能继续实现；
3. 正式流程可用后：产生带版本的 Proposal，多个独立 Reviewer，Finding 全部关闭，Controller 生成 Adoption Decision；Fix 只引用该 Adoption Decision，不复制一套正式方案语义。

### D6：验收后生命周期没有闭环

当前 `run_reopened` 在用户 request-changes/reject 时产生。但 L1 对该事件的语义是：一个已经 ACCEPTED 的 Run 后来发现问题，需要重新调查、修改或验证。

需要分开：

```text
人工返工回流：WAITING_FOR_USER -> INVESTIGATING/IMPLEMENTING/DISPOSITION/BLOCKED
验收后重开：ACCEPTED -> 新的 Fix cycle
```

后验收流程至少要能记录：问题被确认的证据、重开原因、旧 Acceptance/版本被哪个新 cycle supersede、是否执行回滚、回滚对应的真实版本/命令/证据。Extension 不能把“用户请求回滚”当作“回滚已经发生”。

### D7：unverified 策略过于粗粒度

L1 并不是要求所有未覆盖项都自动放行，而是允许在“已明确披露且不影响接受决定”时接受。当前 `unverified: string[]` 只有字符串，没有“阻塞/非阻塞”或接受依据，因此 Runtime 只能采取全拒绝。

**推荐不直接放宽**：先定义结构化验证缺口，例如每项至少包含：缺口说明、影响范围、是否阻塞接受、责任方/补齐条件。然后只有所有缺口都明确为非阻塞、人工决定明确接受、风险已记录时，才允许 ACCEPTED；默认策略仍可保持全拒绝。

### D8：Feature 不是 Fix 的尾项

`feature-扩展.md` 已经是 L1 `DECIDED`，但没有 `packages/feature`。这代表产品语义已经有了，L2 还没开始落地。

**推荐最小路线**：

```text
contracts：discovery / requirement proposal / technical proposal / adoption / blocker
  -> feature definition：阶段、轻量路径、正式方案 Guard
  -> extension：/feature 命令和用户决定
  -> implementation / change review / verification
  -> 测试：正常、轻量、正式评审、回流、阻塞、恢复、版本绑定
```

它应作为独立项目，不能为了减少 Drift 把 Feature 的代码临时塞入 Fix 或 Runtime。

### D9：当前不是 OS 级隔离

现在的 `PiSdkWorkerExecutor` 能创建独立 AgentSession，限制传入的 context/tools/skills，但这只证明：

- Worker 不共享主 Agent 对话历史；
- Worker Profile 声明了允许的工具和 Skill。

它不能证明：

- Worker 不能读取未授权文件；
- Worker 不能访问网络或外部凭证；
- Worker 不能通过 shell 绕过工具白名单；
- Worker 运行在独立进程、容器或受限 worktree。

**推荐路线**：先让产品/安全 owner 明确威胁模型与最低隔离承诺，再按能力等级实现文件、网络、shell 和凭证边界，并做实际越权测试。在实现之前，文档必须继续明确“不把 Session/tools/skills scope 说成 sandbox”。

### T1-T4：技术设计偏差

- **T1 双泛型**：不影响运行，优先修文档或明确“单泛型是采纳的实现简化”。
- **T2 Audit**：影响 L1 指标能否计算和“100% ACCEPTED 有审计”的可信度，是技术层最重要的偏差。
- **T3 事件位置**：当前是设计取舍，不急于迁移；未来扩展多种 Workflow 时再解决 namespace/通用事件边界。
- **T4 空 Skill**：应统一 parser 语义，让显式 `skills: []` 表示“明确不加载 Skill”并通过校验；未知、重复和格式非法仍拒绝。

## 3. 推荐解决方案的阶段顺序

### Phase 0：先修事实文档

范围：只修 L2 README 和 L2 技术设计中的过期实现状态，不改行为。

- 删除已清理 legacy `fixDefinition` 的旧描述；
- 把技术设计 §8 的“当前尚未实现”更新为当前事实，保留真正未实现项；
- 将 T1-T4 和当前 Fix Drift 互相链接；
- 做仓库内 Markdown 相对链接检查。

完成标准：README、技术设计、源码/测试对当前状态没有互相矛盾的陈述。

### Phase 1：Fix 证据与报告投影（当前实施）

范围：D2 + 报告相关的最小合同补齐。

- 调整 Intake 合同：新 Run 产出有长度边界的 `summary` 和 `overview`；原始 `problem` 作为 Run 的输入/追溯事实保存，但不直接展示；旧 `phenomenon` 进入兼容降级路径；
- 增加 Investigation 结构化字段，并定义字段 owner；
- 完善 Verification 的命令/检查、验证结论和结构化缺口；
- 报告按 L1 六大节输出，缺事实写“无/尚未确认”；
- 报告和 `WAITING_FOR_USER` 摘要从 Intake 的 `summary`/`overview` 投影，不直接依赖命令参数；
- 状态字面可以保持“已解决”作为 ACCEPTED 的普通默认，但 `mitigation`/`explanation` 要能准确显示“已缓解/无需修改”；这不改变人工最终验收控制；
- 补充缺字段、字段类型错误、摘要/概要超长、旧 `phenomenon` Artifact、时间线证据引用、非仓库变更和历史 checkpoint 兼容测试。

完成标准：报告的每个 L1 模板字段都有唯一数据来源；用户原始输入不直接进入报告；Intake 的 `summary`/`overview` 可稳定投影且不重复承载 Investigation 内容；缺失字段明确显示；现有测试和新增测试全绿。

### Phase 2：Fix 等待与阻塞路由（当前实施）

范围：D3 + D4。

- 增加 `pendingDecisionKind` 或同等结构化字段，区分处置前等待和最终验收；
- `wait_decision` 进入处置等待；用户决定只能推进到明确目标；
- `external_action` 只有外部动作完成证据才能进入后续验证；
- Verification 结构化区分 failed / blocked / passed；缺条件进入 BLOCKED，合同错误仍走重试/暂停；
- BLOCKED 解锁必须记录解除条件、补充信息和返回阶段；
- 增加所有等待/阻塞/恢复/重复决定/过期 request 测试。

完成标准：任何“等待用户/外部动作/缺少验证条件”的路径都不会进入验证通过或 ACCEPTED；所有恢复路径有 checkpoint 和原因。

### Phase 3：正式方案升级（当前先实现安全门）

范围：D5。

- 先定义 Fix 与 Core Proposal/Review/Adoption 的交接合同；
- `requiresFormalPlanReview=true` 时，若正式流程不可用立即 BLOCKED；
- 正式流程可用后，Fix 只引用 Adoption Decision 的固定版本；
- 方案修改导致版本变化时使旧 Review/Adoption 失效并重审。

完成标准：没有正式采纳证据的方案不能进入实现；测试覆盖升级、Finding 回流、版本变化和恢复。

### Phase 4：Audit 真实落盘（当前实施）

范围：T2。用户已确认实施。当前只做结构化 Audit 的真实接入、持久化、幂等/失败语义和事件测试；不扩展为 D6 的完整 Bug 记录、验收后重开或复盘系统。

- 为 Fix 注入真实 `AuditSink`，定义 append-only 存储、幂等键、事件版本和失败可见性；
- 补齐 `disposition_completed`、`implementation_created`、`change_review_completed`、`verification_completed` 等真实 emit 点；
- 指标 Projector 只消费结构化 Audit，不从 Trace 或 UI entry 猜测；
- 测试重复事件、乱序/迟到、sink 失败、恢复和旧事件兼容。

完成标准：每个需要审计的 Run 都有可查询 Audit；审计失败不会静默造成“看似完整”的结果。验收后重开、回滚和逃逸复盘不属于本阶段。

### Phase 5：低优先级治理与 parser 收敛

范围：D1 + D7 + T1/T3/T4。当前先实施 D7 的严格默认与 T4 parser 收敛；D1 Arbiter、T1/T3 设计取舍不阻塞当前 Fix。D6 继续延后，等待统一 Bug 记录与复盘基础。

- 先统一 Finding 状态、required 规则、版本绑定和关闭权限；
- 再实现满足独立性约束的 Arbiter；
- 定义结构化 unverified gap 和非阻塞接受条件，决定是否放宽默认策略；
- 统一显式 `skills: []` parser 语义；
- T1/T3 只在有真实消费者时处理，不为类型或目录形式做大迁移。

完成标准：争议可以独立裁决且不能自审；非阻塞缺口的接受有明确证据和人工决定；策略 parser 语义一致。

### Phase 6：独立 Feature 与隔离专项（不纳入当前 Fix）

D6、D8 与 D9 不作为当前 Fix 收尾的隐式附带工作：

- Feature 单独方案、独立评审、独立 package 和测试；
- Isolation 先做 threat model，再决定工具包装、worktree、子进程、容器或网络代理；
- 在真实隔离没有验证前，不更新文档为“完整隔离已实现”。

## 4. 方案中的关键待决策

以下问题不能从当前源码自动推导，需要产品/架构 owner 决定：

1. `external_action`、`change_request`、`wait_decision` 是否允许最终进入 `ACCEPTED`？每类需要什么完成证据？
2. 处置阶段的用户决定与最终人工验收是否复用同一个 `WAITING_FOR_USER` Stage？推荐复用 Stage、增加 `pendingDecisionKind`。
3. Verification 缺少外部条件时，是否由 Verifier 提交结构化 `blocked` 结果，还是由 Controller 生成 blocker？推荐 Worker 提交事实、Controller 生成状态迁移。
4. `requiresFormalPlanReview=true` 且 Core 正式方案流程尚未实现时，是否一律 BLOCKED？推荐是。
5. 是否允许非阻塞 `unverified` 在人工明确接受后进入 ACCEPTED？推荐先保持默认全拒绝，等结构化缺口和指标成熟后再决定。
6. AuditSink 失败时，是否阻止 ACCEPTED，还是允许 ACCEPTED 但标记 `audit_incomplete`？L1 第一阶段“100% ACCEPTED 有审计”更支持阻止完成或进入明确 degraded 状态，不能静默成功。
7. Feature 与 Isolation 是否现在立项？推荐不阻塞 Fix，但分别建立独立方案。
8. D6 后续由哪个系统承载统一 Bug 记录、观察窗口和复盘结果？当前不需要决策，先延后。

## 6. 评审记录

本节由独立评审 Agent 填写。评审 Agent 只报告，不修改本文档、代码或配置。主 Agent 必须保留分歧，不把未解决 finding 伪装成采纳结论。

### 产品语义 / 指标轴

第二轮独立评审：`product_aligner`，结论 `REVISE`，无 P0。

- P1：`problem`、`phenomenon`、`summary`、`overview` 的语义必须分开；原始 `problem` 不能丢弃，但也不能直接渲染；`phenomenon` 是既有 L1 用户现象语义，不能简单当作废弃字段。
- P1：D3 等等待态必须区分处置决定、外部动作完成和最终验收；D4 无仓库变更路径不能无条件回 IMPLEMENTING；D5 不能只依赖 Worker 自报 `requiresFormalPlanReview`；D6 必须定义同一 Run/new cycle、旧 Acceptance 不可变等生命周期语义。
- P2：D7 是当前 L2 的保守策略差异，不是未定义的 L1 语义；`summary`/`overview` 的“两三句话”属于 L2 展示约束，不能未经采纳升级成 L1 硬规则。

### 实现 / 运营轴

第二轮独立评审：`solution_reviewer`，结论 `REVISE`，无 P0。

- P1：当前合同、Pi schema 和 prompt 尚未包含 `summary`/`overview`；需明确 schema 版本、双读/单写迁移、长度上限和投影优先级。当前 checkpoint 已保存 `problem`，但尚未形成更明确的 Run-level immutable input contract。
- P1：Acceptance 仍存在绕过风险：`decide()` 不强制检查 `acceptance.passed`，未知 marker 会被跳过，部分 Review/Verification 版本字段可选；不能等报告重构后再补。
- P1：D3/D4/D5、T2 AuditSink、D6 reopen/rollback 的核心控制和真实证据仍不足；AuditSink 可选且异常静默，Fix 未真正接入持久审计；真实 provider/API/E2E、并发、崩溃恢复和部分失败测试缺失。
- P2：D9 在当前实现中仍只能声称 Session/Skill/工具声明层面的隔离，不能声称 OS sandbox；T4 的“空 Skill”问题应先统一活动 parser 真相源。

### 评审后修订

本轮根据用户反馈修订 D2：

```text
原始 problem：Run 追溯输入，不直接展示
Intake.summary：一句话问题摘要
Intake.overview：两三句话场景/影响概要
Intake.environment/scope/urgency：独立结构化字段
Investigation：预期/实际/确认/根因/时间线/证据缺口

```

保留的分歧：产品评审建议 `overview` 只做展示派生值；用户偏好保留“摘要 + 概要”两个层次；因此方案暂按两个 L2 字段设计，同时保留将 `overview` 降为 UI 投影的备选，不把它写成 L1 硬契约。
