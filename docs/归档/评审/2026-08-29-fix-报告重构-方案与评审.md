## 0. 太长不看

- **问题**：`/fix` 流水线跑完后生成的「最终处置报告」，结构不符合 L1 规定的固定模板：状态一律写「已解决（验收通过）」，且预期-实际行为、确认结果、时间线、已排除候选、证据缺口等关键块没有数据可写。

- **已按用户决策收敛**：三类型路由本次不动（留 drift#2）、字段归属按评审定、兼容用「出现即校验」。

## 1. 背景：drift 是什么

`docs/02-产品实现/README.md` 的「已知 L1 / L2 Drift」表第一行记录了：

> 最终处置报告使用 L1 固定结构 → 当前 `buildFixReport` 为简化 8 节投影，缺 L1 模板的预期-实际-确认结果、时间线表、已排除候选、证据缺口、影响链、处置范围、已执行命令与「需要你决定或协助」；且「状态」硬编码为「已解决（验收通过）」，未区分可允许的「已缓解 / 无需修改」。

拆成两个子问题：

1. **状态硬编码**：不管处置类型是什么，报告一律写「状态：已解决（验收通过）」。
2. **字段缺失**：L1 模板要求的预期/实际、确认结果、时间线表、已排除候选原因、证据缺口、处置范围理由、「缺少验证条件或证据不足」——**根本没有数据可写**。

## 2. 现状代码事实

### 2.1 报告现在长什么样

`packages/fix/src/extension-v2.ts` 的 `buildFixReport`（约 289–348 行）输出简化 8 节：

```
# Fix 处置结果
## 结论
- 状态：已解决（验收通过）          ← 硬编码
- 处置类型 / 风险 / 未验证 / 剩余风险
## 现象        ← 来自 continueRun 传入的 problem 参数，不是 intake artifact
## 根因        ← rootCause + evidence 列表
## 影响面      ← evidence 列表
## 处置        ← dispositionType / 是否仓库变更 / 最小范围 / 风险 / 验证目标
## 修改        ← implementation.summary / filesChanged / 候选版本
## 验证        ← evidence / 未验证 / 剩余风险
## 引用        ← 候选版本 / 处置结论 / 评审结论
```

### 2.2 合同现在有什么

`packages/workflow-contracts/src/index.ts`：

```ts
// intake：现象、环境、范围、紧急度（L1「INTAKE 记录现象、环境、范围、最小事实和初步紧急度」已满足）
export interface IntakeArtifact {
  kind: 'intake';
  phenomenon: string;
  environment?: string;
  scope?: string;
  urgency?: 'low' | 'medium' | 'high' | 'critical';
  [key: string]: unknown;
}

// investigation：只有根因 + 证据 ← 缺口在这里
export interface InvestigationArtifact {
  kind: 'investigation';
  route: InvestigationRoute;
  rootCause: string;
  evidence: EvidenceItem[];
  id?: string;
  [key: string]: unknown;
}
```

校验（index.ts 约 192–201 行）也只检查 `route/rootCause/evidence`。

> **关键机制**：structured artifact 的合同就是给模型的产出约束（Pi SDK structured-output）。合同没定义字段 → 模型不会稳定产出 → 没有测试保障 → 报告不能依赖。所以「报告渲染不出来」的根子在合同，不在渲染代码。

### 2.3 人工验收时看到什么

`WAITING_FOR_USER` 阶段推送的是「# Fix 结果待确认」摘要（现象/根因/处置/变更/验证/风险/未验证/评审结论），**没有状态字样**；报告（含「已解决」）在人工 approve **之后**才生成。

含义：状态措辞不是控制面（不影响验收决定），只影响事后回查报告的人。

## 3. L1 契约要求（`fix-扩展.md`）

- 报告使用**固定结构**，由 Controller 根据**已校验 Artifact** 生成；不得把 Worker 自由文本当报告事实。
- 没有事实的字段写「无」或「尚未确认」，**不得省略或以泛化措辞掩盖**。
- 状态映射：ACCEPTED 可显示「已解决 / 已缓解（只修表面故障点）/ 无需修改 / 经明确接受决定的有限未解决」。
- 模板大节（简化列）：结论（状态/问题类型/根因状态/一句话结论）、现象与问题确认（预期行为及依据/实际行为/确认结果/影响范围）、根因分层与因果证据链（最终根因/停止调查理由/时间范围/T0–T4 时间线表/已排除候选/证据缺口）、影响面与已采取的处置（触及链路/连带场景/未覆盖影响面/处置/相关文件/处置范围）、验证结果（原始问题/回归与兼容/已执行命令/验证结论）、风险与后续（剩余风险/需要你决定或协助）。

## 4. 原方案（提交评审的版本）

1. `InvestigationArtifact` 新增可选字段并加校验：
   `expectedBehavior`、`actualBehavior`、`confirmation: 'reproduced'|'indirect_evidence'|'unconfirmed'`、`impactScope`、`excludedCauses[]`、`stopReason`、`timeline[]({at,event,layer,evidence,role})`、`evidenceGaps[]`；补 contracts.test。
2. `buildFixReport` 改为按 L1 6 大节渲染，缺字段写「无/尚未确认」。
3. 状态不再硬编码：`explanation→无需修改`、`mitigation→已缓解`、其余→已解决。
4. 更新 fix 测试断言。

## 5. solution_reviewer 评审结论（REVISE，无 P0）

| 严重度 | 评审意见 | 说明 |
|---|---|---|
| P1 | 状态不能「其余→已解决」 | `external_action`/`change_request`/`wait_decision` 在 ACCEPTED 时的语义未定义；L1 只允许四种状态，不能默认已解决 |
| P1 | 字段唯一 owner 未闭合 | `stopReason` 与 `investigation_review.stopReason`、`evidenceGaps` 与 review `gaps`/verification `unverified` 语义重叠，报告会混写调查结论 vs 复核结论 vs 验证缺口 |
| P1 | 时间线要证据化 | `timeline[].at/evidence` 需强制 ISO 时间 + 证据引用，否则模型自由文本被当运行事实渲染；禁止从 Trace/自由文本补全时间线 |
| P1 | 兼容与校验强度未定义 | 字段全可选 + `[key:string]:unknown` 下，旧形状 Artifact 仍可进 ACCEPTED 生成「已解决」报告；需定义「出现即校验」或 schema 迁移 |
| P1 | 人工验收摘要必须同步 | 只改最终报告不够：`WAITING_FOR_USER` 待确认摘要与 `/fix review` 详情也应展示预期-实际-证据链（复用同一投影器），否则人可能在看不到关键事实时 approve |
| P2 | 未列 drift 更新计划 | 实现完应同步改 README drift 行，避免文档仍声称未修复 |
| P2 | 自由文本治理 | 新字段限长/数组上限/敏感信息不落盘，优先用 `EvidenceItem.ref` 引用 |
| — | 细节修正 | 报告「现象」应从 `intake.phenomenon` 投影，而不是 `reportProblem` 参数直接塞 |

**评审要求必须修改 4 项**：字段到报告块的唯一来源映射、完整状态/路由映射（禁止其余→已解决）、验收摘要同步增强、时间线/命令/旧 checkpoint 兼容测试。

**评审留下 3 个待用户决策**：
- `external_action`/`change_request`/`wait_decision` 在 ACCEPTED 下是否允许「有限未解决」及各自完成证据；
- `stopReason`/`evidenceGaps` 与复核/验证相关字段的最终归属；
- 新字段仅对新 Run 强制，还是升级 schema 迁移旧 checkpoint。

## 6. 修订方案（已按用户决策收敛）

| 决策点 | 定论 | 理由 |
|---|---|---|
| A. 三类型路由 | **本次不动**，`external_action`/`change_request`/`wait_decision` 维持现状走原流程，与 drift#2（`disposition→需要用户/外部决定→WAITING_FOR_USER` 虚线边）一起做 | 控制范围，避免本次牵动 guard；状态措辞非控制面（人工验收兜底） |
| B. 字段 owner | 预期/实际/确认/影响面/已排除候选/停止调查理由/证据缺口归 `investigation`；`review.gaps` 与 `verification.unverified` 作为**独立小节**显示，不与调查结论混写 | 评审建议的两层归属 |
| C. 兼容 | 新字段全部可选 +「出现即校验」（提供则类型/枚举/时间格式必须正确，不提供不报错）；不引入 schema 迁移；报告缺字段写「无/尚未确认」 | 当前无真实持久化数据，迁移成本不值 |
