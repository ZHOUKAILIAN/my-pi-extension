# Design Review: Work/Build/Bug Governance Runtime

- Date: 2026-08-18
- Reviewer model: `smartingredients/gpt-5.6-sol`
- Review mode: three independent read-only runs with separate scopes
- Repository revision reviewed: working tree after `c23ec7c`
- Result: changes required before implementation

## Reviewers

| Scope | Focus |
|---|---|
| Entry router | `build` requirement/design alignment, `work` classification, `bug` root-cause escalation |
| Runtime isolation | Policy, Skill Routing, Context Capsule, Capability Isolation, Pi CLI resource loading |
| Workflow gates | multi-agent proposal/challenge, cross-review, rebuttal, arbiter, revision and state transitions |

## Findings

### P0: State transitions can bypass required gates

The original `work` and `bug` diagrams stopped at `DESIGN_PROPOSING` and then moved to `CROSS_REVIEW`. The design did not define a complete requirements alignment protocol either. An implementation could therefore approve a proposal without challenge or arbiter decision.

Action: define shared requirement and design alignment subflows and prohibit direct transitions from alignment/proposal to implementation or review.

### P0: Final evidence was not bound to the final code revision

A reviewer may inspect one diff, the implementer may change the code, and the verifier may still use the old review or test result. Every review finding, disposition and verification result must bind to a candidate revision or diff digest. Any code change invalidates downstream evidence.

Action: add `candidateRevision`/`diffDigest` to review and verification artifacts and make revision changes return the run to `CROSS_REVIEW`.

### P0: Runtime isolation was overstated

`--no-extensions` prevents automatic extension loading but does not stop a worker with `bash` from spawning another Pi process. `--no-skills`, Pi tool allowlists and worktrees also do not provide OS-level path, network, credential or process isolation.

Action: document these as resource/configuration controls only. Capability isolation requires restricted tools, process policy, filesystem/network controls, and eventually a trusted sandbox/container.

### P1: Work and bug routing was ambiguous

The original glossary said only “the latter two” routes automatically entered design alignment, although the listed categories did not make that unambiguous. It also allowed a bug to be treated as a local work item without an explicit root-cause investigation.

Action: make `build`, `work` and `bug` routing explicit. Existing behavior anomalies enter `bug`; `bug` investigation can produce `local_fix`, `requirement_change`, `design_change`, `needs_more_evidence` or `blocked`.

### P1: Context Capsule conflicted with automatic context loading

The design said workers receive only a minimal capsule while also recommending inherited `AGENTS.md` context. Pi can load global and ancestor context files automatically, so those files are extra inputs unless explicitly listed and hashed.

Action: strict mode uses `--no-context-files` and injects an allowlisted, hashed project-instruction artifact into the capsule. In inherited-context mode, every loaded context file must be part of the manifest and trace.

### P1: Finding closure and review independence were underspecified

An implementer response such as “accepted” or “fixed” is not itself a closed finding. Role names also do not guarantee independent workers.

Action: separate implementer disposition from reviewer/arbiter resolution, require distinct worker IDs for proposal/challenge/arbiter and implementer/reviewer/verifier, and calculate acceptance in the runtime.

## Accepted Direction

The overall direction remains valid:

- `build` always starts with multi-agent requirement and design alignment.
- `work` classifies before choosing local, requirement-change or design-change flow.
- `bug` investigates first and upgrades to design alignment only when the minimum acceptable fix changes an established technical boundary or decision.
- The first worker runtime can remain a child Pi CLI process, but the implementation must use fail-closed policy checks and must not claim CLI flags are a sandbox.

## Arbiter Follow-up

A final independent `smartingredients/gpt-5.6-sol` arbiter reviewed the revised documents and classified the original four risk groups as closed, with no remaining P0. It identified four P1 implementation gaps: route schema mappings, `BLOCKED`/`BLOCKED_DECISION` consistency, the requirement proposer Role, and mandatory revision-bound verification output.

Those four gaps were fixed in the working tree:

- Work and Bug now use discriminated route decisions with explicit target stages.
- `BLOCKED` is the only runtime state; `blockReason` identifies the unlock rule.
- `requirement_proposer` is included in the Policy Role enum.
- `RevisionBoundResult` and `VerificationResult` make candidate revision and diff digest mandatory for review and verification stages.

The design is now approved for Phase 0 implementation planning, not for claiming runtime isolation. CLI, context manifest, shell wrapper, process, and sandbox failure tests remain required before implementation behavior is accepted.

## Decision

**APPROVED FOR PHASE 0, NOT APPROVED FOR PRODUCTION IMPLEMENTATION.**
