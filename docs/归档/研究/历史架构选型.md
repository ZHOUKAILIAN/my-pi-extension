# 多 Agent Pi Extension 技术方案选型

> 归档说明：这是历史研究材料，不是当前架构或运行事实的正式真理源。当前产品语义、实现和项目落地分别以第一层、第二层和第三层为准。

## 1. 要解决的问题

希望把 `work`、`build` 一类开发任务从“一个主 agent 自行读代码、改文件、自己确认完成”的模式，变为有强制协作门禁的工程流程：

1. 技术方案由多个独立角色提出、质疑、收敛。
2. 实现工作委派给有边界的 worker agent。
3. 代码审查不是实现者自审；至少存在交叉审查和独立验证。
4. 主 agent 不可绕开委派机制直接使用项目读写/执行工具。
5. 系统按照任务阶段和角色，控制可发现/调用的 skill、可见上下文和实际能力。
6. 系统保留从用户需求到最终验证结论的完整证据链。

Pi 原生提供 extension、工具、事件、CLI 和 SDK，但**没有内建的 subagent 编排产品能力**。因此这个仓库实现的是 Pi 上层的**工作流治理 runtime**，而不是接一个已有的 Pi 原生 `subagent` API。

术语以当前第一层的 [领域术语](../../01-产品定义/领域术语.md) 为准。这里特别区分三个不能混用的控制面：

| 控制面 | 解决的问题 | 第一版机制 | 是否是安全边界 |
|---|---|---|---|
| Skill Routing | 这个角色可使用哪些工作方法 | `--no-skills` 加显式 `--skill <path>`，加上 Policy 校验 | 否 |
| Context Isolation | 这个角色本轮能看到哪些信息 | 最小 Context Capsule；只传允许的 Artifact，不传主会话全文 | 否 |
| Capability Isolation | 这个角色实际能读、写、执行什么 | Pi 工具白名单、shell wrapper、worktree/容器、自定义工具 | 是，前提是底层隔离可信 |

## 2. 入口路由：Work、Build 和 Bug

这套 runtime 的入口不是泛化的“任意任务”，而是工作中已有的三类操作。入口决定第一阶段和是否必须进入多 agent 方案对齐。

| 入口 | 默认含义 | 第一阶段 | 何时进入多 agent 方案对齐 | 何时可以走轻量路径 |
|---|---|---|---|---|
| `build` | 新需求、新用户目标或新能力 | 需求对齐 + 方案提议 | **总是进入**，先形成批准方案和验收标准 | 不允许跳过；需求很小时可减少角色数量，但不能取消独立质疑和裁决 |
| `work` | 对已有代码/功能继续工作 | 任务分类 + 事实调查 | 发现需求行为变更、技术方案变更、跨模块契约变化或高风险决策时进入 | 已确认是局部实现/局部修复，且不改变既有方案时，可直接进入受控实现 |
| `bug` | 已有行为异常或回归 | 事实、影响面、根因调查 | 根因要求改变架构、模块边界、数据/API 契约、核心状态机或既有技术决策时进入 | 根因明确且修复保持既有技术方案、影响面局部时，走局部修复 + review + verify |

### `build` 状态机

```text
BUILD_RECEIVED
  -> REQUIREMENT_ALIGNMENT
  -> REQUIREMENT_CHALLENGING
  -> REQUIREMENT_DECIDING
  -> DESIGN_PROPOSING
  -> DESIGN_CHALLENGING
  -> DESIGN_DECIDING
  -> IMPLEMENTING
  -> CROSS_REVIEW
  -> VERIFYING
  -> ACCEPTED | CHANGES_REQUESTED | BLOCKED
```

`work`/`bug` 的任何分支只允许汇入上述共享子流程或 `IMPLEMENTING`，不允许从分类、调查、需求对齐或设计提议直接进入 review/accept。`CHANGES_REQUESTED` 只能回到 `IMPLEMENTING`，并受 `maxRevisionAttempts` 限制。阻塞统一使用 `BLOCKED`，由 `blockReason: "decision_required" | "insufficient_evidence" | "verification_blocked" | "policy_violation"` 区分；只有对应的用户决策 Artifact、新证据、验证恢复或 Policy 修复可以解锁。文档中的 `BLOCKED_DECISION` 只是 `blockReason: "decision_required"` 的显示标签，不是第二个状态。

### 统一对齐子流程

`build`、`work` 和升级后的 `bug` 都只能通过显式的对齐子流程进入实现：

```text
REQUIREMENT_ALIGNMENT
  -> REQUIREMENT_CHALLENGING
  -> REQUIREMENT_DECIDING
  -> DESIGN_PROPOSING
  -> DESIGN_CHALLENGING
  -> DESIGN_DECIDING
  -> IMPLEMENTING
```

需求对齐至少产出：需求目标、范围、验收标准、未决项和独立质疑的逐项裁决。设计对齐至少产出：可比较方案、权衡、风险、验证方式和独立质疑的逐项裁决。不存在从 `REQUIREMENT_ALIGNMENT` 或 `DESIGN_PROPOSING` 直接进入 `CROSS_REVIEW` 或 `IMPLEMENTING` 的合法状态边。

### `work` 状态机

```text
WORK_RECEIVED
  -> CLASSIFYING
  -> [LOCAL_CHANGE -> IMPLEMENTING]
  -> [REQUIREMENT_CHANGE -> REQUIREMENT_ALIGNMENT]
  -> [DESIGN_CHANGE -> REQUIREMENT_ALIGNMENT]
  -> [NEEDS_MORE_EVIDENCE | BLOCKED -> BLOCKED]
  -> CROSS_REVIEW
  -> VERIFYING
  -> ACCEPTED | CHANGES_REQUESTED | BLOCKED
```

### `bug` 状态机

```text
BUG_RECEIVED
  -> INVESTIGATING
  -> ROOT_CAUSE_DECIDING
  -> [LOCAL_FIX -> IMPLEMENTING]
  -> [REQUIREMENT_CHANGE -> REQUIREMENT_ALIGNMENT]
  -> [DESIGN_CHANGE -> REQUIREMENT_ALIGNMENT]
  -> [NEEDS_MORE_EVIDENCE | BLOCKED -> BLOCKED]
  -> CROSS_REVIEW
  -> VERIFYING
  -> ACCEPTED | CHANGES_REQUESTED | BLOCKED
```

`bug` 不能仅因为“这是 Bug”就自动进入完整方案评审；升级条件必须由调查产物明确记录“最小可接受修复必须改变既有技术方案”。反过来，`work` 也不能因为看起来是小改动就绕过分类。分类/调查 worker 必须输出机器可校验的专用结果：

```ts
type WorkRouteDecision = {
  entry: "work";
  route: "local_change" | "requirement_change" | "design_change" | "reroute_bug" | "needs_more_evidence" | "blocked";
  targetStage: "IMPLEMENTING" | "REQUIREMENT_ALIGNMENT" | "BUG_INVESTIGATING" | "BLOCKED";
  evidence: string[];
  behaviorChanged: boolean;
  contractChanged: boolean;
  designChanged: boolean;
  riskLevel: "low" | "medium" | "high";
  reason: string;
};

type BugRouteDecision = {
  entry: "bug";
  route: "local_fix" | "requirement_change" | "design_change" | "needs_more_evidence" | "blocked";
  targetStage: "IMPLEMENTING" | "REQUIREMENT_ALIGNMENT" | "BLOCKED";
  evidence: string[];
  behaviorChanged: boolean;
  contractChanged: boolean;
  designChanged: boolean;
  riskLevel: "low" | "medium" | "high";
  reason: string;
};

type RouteDecision = WorkRouteDecision | BugRouteDecision;
```

如果 Work 调查发现已有行为异常或回归，必须重路由为 Bug；不能直接选择 `local_change`。如果 Bug 的实际结论是需求变化，则进入需求对齐，不把需求问题伪装成技术方案变更。

## 3. 概念与职责

```text
用户
  -> 主 agent（任务判断和阶段推进）
  -> delegate_task extension tool（权限控制、启动 worker、记录 trace）
  -> worker Pi agent（完成一个边界明确的子任务）
  -> 结构化结果回到主 agent / 协调器
```

### 主 agent

主 agent 是编排决策者，不是默认执行者。它只允许调用 `delegate_task`、读取 worker 的结构化结果，并根据阶段门禁决定下一步。它不能直接调用 `read`、`bash`、`edit`、`write` 等项目操作工具。

### Policy 与 `delegate_task`

Policy 是版本化的唯一控制源，至少定义：阶段状态迁移、Role、工具白名单、skill 白名单、上下文规则、产物 schema、预算和批准条件。`delegate_task` 是本 extension 提供的工具，不是 Pi 自带工具；它解释并执行当前 Policy：

- 校验当前阶段允许委派哪个角色；
- 按角色和阶段生成 Context Capsule、worker prompt、工具白名单和 skill 白名单；
- 启动/取消 worker；
- 收集 stdout、退出码、工具事件、耗时和 token usage；
- 校验 worker 输出的结构化结果；
- 将结果和 trace 写入 session 或本地 trace 文件。

这意味着主 agent 不能自行决定“现在加载一个额外 skill”或“把所有历史发给 reviewer”。它只能请求委派，extension 依据 Policy 决定该请求是否有效。

### Worker agent

Worker 是一个独立运行的 Pi agent，不是 extension 自己实现一套 LLM loop。第一版由 extension 调用子 Pi CLI 进程启动；Pi 仍负责模型调用、工具调用和 agent loop。

Worker 必须只承担一个完整子任务，例如“只读定位根因”“提出方案并列出权衡”“按既定设计修改代码”“独立执行验证”“审查某个指定 diff”。不要为每次 `read` 或每条 shell 命令启动一个新 worker。

每个 Worker 只收到一个 Context Capsule：任务目标、角色约束、基准版本、验收条件、允许的 Artifact 引用、允许 skill 路径以及必要文件引用。默认不继承主 agent 的完整对话、其他 worker 的隐藏推理或全局 skill 清单。

子 Pi 使用 `-p --no-session` 时会启动新的 Pi session，不会自动继承主 session 的消息树；这正适合 worker 隔离。worker 获得什么信息，必须由 `delegate_task` 显式放入 Context Capsule 或由允许的资源发现规则加载。

### Policy 最小模型

第一版不应把策略写死在 TypeScript 的 `if/else` 里。将策略存为版本化 JSON/YAML，extension 只做 schema 校验和执行。例如：

```ts
type RolePolicy = {
  role: "investigator" | "requirement_proposer" | "architect" | "challenger" | "implementer" | "reviewer" | "verifier" | "arbiter";
  allowedStages: string[];
  tools: string[];
  skillPaths: string[];
  allowedArtifactTypes: string[];
  context: {
    mode: "strict" | "inherited";
    includeUserGoal: boolean;
    includeProjectInstructions: boolean;
    includeFullSession: false;
    maxArtifactBytes: number;
  };
  writeMode: "none" | "current-worktree" | "isolated-worktree";
  budget: { maxWorkers: number; maxDurationMs: number; maxTurns?: number; maxRevisionAttempts: number };
};
```

实际启动 worker 时，Policy 映射为 Pi CLI 参数和 Context Capsule：

```text
Policy.tools       -> --tools <allowlist>
Policy.skillPaths  -> --no-skills + repeat --skill <path>
Policy.context     -> 由 extension 构造 workerPrompt，不转发主 session
writeMode          -> cwd / 临时 worktree / 容器及对应文件系统权限
allowedArtifacts   -> capsule 内可引用/展开的 artifact 白名单
budget             -> timeout、并发锁、轮次和成本阈值
```

这样 skill 选择本身也能审计：trace 应记录某次委派实际允许了哪些 skill 路径、worker 是否读取了该 skill、以及它产出了哪个 Artifact。

## 4. 方案选项

| 方案 | 实现方式 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| A. 子 Pi CLI worker | extension 用 `pi.exec()` 启动 `pi -p` | 进程隔离清晰；复用现有认证、模型、工具；容易观察和 kill；首版实现小 | 初期只能从 stdout 得到结果；需设计输出协议和并发控制 | **第一版采用** |
| B. Pi SDK in-process worker | extension 内用 `createAgentSession()` 创建内存 session | 可订阅 tool/message 事件；有类型和 usage；更适合并发、细粒度 trace | 生命周期、资源加载、认证、取消和 session 隔离复杂；容易与宿主 runtime 混淆 | 第二阶段演进 |
| C. 引入已有 agent-team/package | 安装并适配一个既有协作运行时 | 可能较快获得团队管理能力 | 依赖的协议、持久化和权限模型未验证；会把核心控制权交给外部实现 | 先调研，暂不作为基础 |

### 推荐：A，子 Pi CLI worker

典型执行形态：

```ts
const result = await pi.exec(
  "pi",
  [
    "-p",
    "--no-session",
    "--no-extensions",
    "--tools",
    workerTools,
    workerPrompt,
  ],
  { signal },
);
```

这里的关系需要明确：

- `delegate_task` 是本项目写的 extension 工具；
- 子进程里的 agent、模型调用和 `read`/`bash`/`edit`/`write` 工具仍然由 Pi 提供；
- `--no-extensions` 防止 worker 自动发现本 extension，但**不能**阻止拥有 `bash` 的 worker 自己启动嵌套 Pi、Node 或其他进程；
- worker 在当前项目 `cwd` 运行，允许写入时修改会直接落到当前 worktree；
- `-p` 只适合最小原型的结果回收，不能可靠提供逐项工具事件、skill 读取证据或 usage；Phase 0 必须并行验证 `--mode json` 或 RPC 的事件记录能力。

Context Capsule 有两种明确模式，不能混称“唯一输入”：

- **strict capsule mode**：worker 用 `--no-context-files`；runtime 把经过 allowlist、版本固定和 hash 记录的项目规则 Artifact 显式放进 capsule。
- **inherited context mode**：worker 允许自动发现全局、父目录和项目 `AGENTS.md`；所有实际加载的 context file 必须进入 manifest、记录 canonical path 和 content hash，并被视为 capsule 的额外输入。

Skill Routing 的 CLI 原型应为 `--no-skills` 配合角色允许的重复 `--skill <path>`，防止 Pi 自动发现所有全局和项目 skill。Policy 必须固定 canonical path、解析后的 skill 集合与内容 hash，并拒绝越界 symlink。注意：这只控制 Pi 的 skill 发现和 system prompt；拥有 `read`/`bash` 的 worker 仍可能从磁盘访问未授权 skill、读取凭证、访问网络或启动嵌套 agent。因此禁止访问本身要由受限自定义工具、进程策略、只读挂载和最终的容器/OS sandbox 实现。

## 5. 为什么不是“extension 自己编排全部流程”

有两种运行模型：

| 模型 | 谁决定下一步 | 适用情况 |
|---|---|---|
| 固定 pipeline | extension 状态机 | `work`/`build` 的标准流程、需要可预测门禁的场景 |
| 委派工具 | 主 agent | 开放式任务，主 agent 根据结果决定是否继续调查、返工或补验证 |

本项目采用**混合模式**：extension 拥有不可绕过的阶段状态机和权限门禁；主 agent 在允许的阶段内选择具体委派内容和顺序。

这避免两个极端：

- 全交给主 agent：流程会退化为提示词约束，容易绕过。
- 全写死在 extension：每一种工程问题都要重新编码流程，弹性不足。

## 6. 协作工作流

### 6.1 需求与技术方案阶段

需求提案使用 `requirement_proposer` Role；技术方案提案使用 `architect` Role。两者都是独立的 Policy Role，不能仅靠显示名称区分。

技术方案不能由单一 agent 直接进入实现。需求对齐和设计对齐都必须经过独立提案、质疑和裁决：

| 阶段 | 角色 | 输入 | 强制输出 | 通过条件 |
|---|---|---|---|---|
| 调研 | investigator | 用户目标、代码/现状 | 事实、影响面、未知项、证据路径 | 事实与假设显式区分 |
| 需求提案 | requirements A、requirements B | 调研包、用户目标 | 目标、范围、验收标准、未决项 | 独立生成；小任务可一份提案，但必须保留独立质疑和裁决 |
| 需求质疑 | requirements challenger | 需求提案，不提供作者身份 | 歧义、遗漏验收、反例、越界风险 | 每项质疑有稳定 ID 和 disposition |
| 需求裁决 | requirements arbiter | 需求提案、质疑、证据 | 批准需求、验收标准、未决风险 | 不允许未关闭的 blocking challenge 进入设计 |
| 设计提案 | architect A、architect B | 批准需求、现状 | 可比较方案、权衡、风险、验证方式 | 有真实方案分叉时至少两份独立方案 |
| 设计质疑 | challenger A、challenger B | 设计方案，不提供作者身份 | 反例、遗漏约束、失败模式、替代建议 | 每项质疑有稳定 ID 和 disposition |
| 设计裁决 | design arbiter | 设计方案、质疑和证据 | 选型、拒绝理由、未决风险、验收门槛 | 不允许未关闭的 blocking challenge 进入实现 |

最小独立性要求：提案者、挑战者和裁决者必须使用不同 `workerId`。需求很小时可以减少提案数量，但不能取消独立质疑和独立裁决；只有存在真实方案分叉时才要求两份完整方案，不能为了形式制造虚假备选。

`architect A/B` 不是要无休止互相辩论。需求和设计都采用最多两轮的受限协议：

1. 提案者独立生成，互相不可见；每份产物绑定 `workerId` 和输入 Artifact digest。
2. 挑战者独立审查，输出带稳定 ID、证据和严重度的质疑。
3. 提案者可以回应，但只能由挑战者或 Arbiter 正式关闭质疑；只有缺少决定性证据才允许一次定向补充调研。
4. Arbiter 根据事实、质疑 disposition 和验收标准裁决。
5. 达到轮次上限仍无法决定时，状态为 `BLOCKED` 且 `blockReason: "decision_required"`，只能由用户决策 Artifact 解锁，不能由主 agent 猜测性推进。

### 6.2 实现与验证阶段

```text
APPROVED_FOR_IMPLEMENTATION
  -> IMPLEMENTING
  -> CROSS_REVIEW
  -> VERIFYING
  -> ACCEPTED | CHANGES_REQUESTED | BLOCKED
```

| 阶段 | 角色与权限 | 输入 | 输出 | 门禁 |
|---|---|---|---|---|
| 实现 | implementer，唯一写权限 | 已批准决策、验收标准 | diff、变更说明、执行过的检查 | 同一 worktree 同时仅一个写 worker |
| 交叉审查 | reviewer A/B，只读 | 固定 commit/diff、设计决策 | findings，含严重度、证据和建议 | A/B 彼此审查不同来源的实现，或对同一 diff 独立审查 |
| 反驳/修复 | implementer + reviewer | findings | implementer 回应 `fixed_claimed`、`disagree` 或 `blocked`，必要的修复 diff | implementer 无权正式关闭自己的 finding |
| 独立验证 | verifier，只读，允许测试命令 | 验收标准、最终 diff | 实际命令、结果、覆盖缺口、结论 | verifier 不得是本次 implementer；必须绑定最终 revision |
| 最终判定 | 独立 arbiter | review disposition、验证证据 | accepted / changes requested / blocked | runtime 计算：P0/P1 正式关闭、P2 已处置、最终 revision 验证通过；必需验证阻塞只能是 blocked |

“A 给 B、B 给 A 掰扯”应解释为**交叉 review 与受控 rebuttal**，而不是两人互相说服：

- reviewer 只提交带文件/行号、复现方式和风险的 finding；
- implementer 对每项 finding 给出 `fixed_claimed`、`disagree` 或 `blocked`，`disagree` 必须引用证据；
- reviewer 复核后才能产生 `resolved_fixed` 或 `resolved_rejected`，有争议时交给独立 arbiter；
- 对同一 finding 最多一轮 rebuttal；arbiter 裁决后不得重新开启无限辩论；
- 所有 finding、disposition 和 verify 结果绑定同一个 `candidateRevision` 或 `diffDigest`；代码一旦变化，旧证据全部失效并回到 `CROSS_REVIEW`；
- arbiter 不能是当前 proposal、implementer、reviewer 的同一 `workerId`。

## 7. 权限与并发模型

### 主 agent 的工具面

主 agent 只启用：

```text
delegate_task
get_workflow_status
get_artifact
```

extension 需要同时做两层控制：

1. `pi.setActiveTools()` 只激活当前 Policy 精确白名单中的工具，默认拒绝所有其他工具；
2. `tool_call` hook 对任何不在当前 Policy 白名单内的 tool name fail closed，包括之后动态注册的工具。

单靠拦截不够，单靠 system prompt 更不够。Pi 工具白名单只限制模型可调用的 Pi 工具，不限制进程本身的 OS 权限；`bash` 同时拥有文件、网络、进程和凭证访问风险，因此 Capability Isolation 仍需由底层执行环境承担。

### Worker 权限矩阵

| 角色 | 读项目 | 执行命令 | 写项目 | 可启动 worker |
|---|---:|---:|---:|---:|
| investigator | 是 | 只读检查 | 否 | 否 |
| architect/challenger/arbiter | 只读材料优先 | 否或有限 | 否 | 否 |
| implementer | 是 | 是 | 是 | 否 |
| reviewer | 是 | 只读检查/测试 | 否 | 否 |
| verifier | 是 | 是 | 否 | 否 |

Pi 的 `bash` 工具本身无法可靠地区分“只读命令”和“写命令”。第一版中，非 implementer 若需要跑测试，应该使用一个受限 shell wrapper 或隔离 worktree/container；不能仅靠 prompt 声明“不要写”。这是一项必须验证的安全边界。

### 文件与并发

- 写 worker 串行运行；第一版禁止两个 implementer 并发写同一 worktree。
- 只读 worker 可以并行，但应在其输入中固定基准 commit/工作区快照，防止对不同版本得出难以比较的结论。
- 若以后需要并行实现，必须使用独立 worktree 或 patch-only worker，并引入明确的合并者角色。

## 8. 状态、产物与审计

每次任务生成一个 `runId`，保存机器可读状态。建议初期使用 JSON，文档/说明使用 Markdown：

```ts
type DelegationRecord = {
  runId: string;
  taskId: string;
  stage: string;
  role: string;
  workerId: string;
  inputArtifactIds: string[];
  outputArtifactId?: string;
  policyDigest: string;
  contextManifestDigest: string;
  baseRevision: string;
  candidateRevision?: string;
  writeAccess: boolean;
  status: "queued" | "running" | "succeeded" | "failed" | "cancelled";
  startedAt: string;
  finishedAt?: string;
  exitCode?: number;
  usage?: unknown;
};
```

每一个 worker 的输出必须是可校验的结构化结果，而不是一段无法机读的散文：

```ts
type WorkerResult = {
  status: "ok" | "blocked" | "failed";
  summary: string;
  claims: Array<{ statement: string; evidence: string[] }>;
  changedFiles: string[];
  candidateRevision?: string;
  diffDigest?: string;
  commands: Array<{ command: string; exitCode: number; summary: string }>;
  findings: Array<{
    findingId: string;
    severity: "P0" | "P1" | "P2" | "info";
    candidateRevision: string;
    location?: string;
    issue: string;
    evidence: string;
    recommendation: string;
    implementerResponse?: "fixed_claimed" | "disagree" | "blocked";
    formalResolution?: "resolved_fixed" | "resolved_rejected" | "blocked";
  }>;
  risks: string[];
  nextAction: string;
};

type RevisionBoundResult = WorkerResult & {
  candidateRevision: string;
  diffDigest: string;
};

type VerificationResult = {
  status: "passed" | "failed" | "blocked";
  candidateRevision: string;
  diffDigest: string;
  commands: Array<{ command: string; exitCode: number; summary: string }>;
  coverageGaps: string[];
  conclusion: string;
};

// CROSS_REVIEW, finding resolution and VERIFYING use RevisionBoundResult or
// VerificationResult. A result without the final revision cannot pass the gate.
```

输出协议可先让 worker 在最后输出唯一 JSON block；生产化时应改用 Pi custom tool 或 RPC 事件，避免从自由文本 stdout 解析。

应记录的最小证据：

- 原始用户任务和执行时的工作目录/基准 commit；
- 当前 Policy digest、Context manifest digest 和实际加载的 context/skill canonical paths 与 content hashes；
- 每个候选代码 revision 的 commit/diff digest；review、finding、disposition 和 verify 必须绑定该 revision；代码变化后旧 review/verify 自动失效；
- 实际给每个 worker 的 prompt、角色、工具白名单和输入材料版本；
- 每个 worker 的退出码、输出、耗时、usage 与失败原因；
- 实现 diff；
- 所有 review finding、implementer response、formal resolution 和 disposition；
- 验证命令、实际结果、验证对应的 candidate revision 和残余风险；
- 最终裁决者、结论及其依据。

## 9. 风险与反形式主义机制

| 风险 | 后果 | 控制 |
|---|---|---|
| 多个 agent 都继承同一错误前提 | 看似有共识，实为同源错误 | 提案独立生成；challenge 先看证据后看结论；必要时引入专门的反证角色 |
| agent 无限互评 | 成本失控，决策不收敛 | 固定轮数、finding 格式、arbiter 裁决、`BLOCKED` + `blockReason: "decision_required"` 升级给用户 |
| implementer 自审或 verifier 复用实现结论 | 验证失效 | 角色隔离；不同 worker ID；verifier 只读且必须给出实际命令输出 |
| worker 递归/逃逸执行 | `--no-extensions` 仍可被 `bash` 绕开以启动嵌套 Pi 或其他进程 | 禁用不必要的 bash；进程策略、凭证隔离和 OS sandbox；不把 CLI flag 当作安全边界 |
| Policy/Artifact/trace 被写 worker 篡改 | 后续委派被错误规则或证据驱动 | 控制平面置于 worker 不可写位置；每个 run 固定 Policy/Artifact hash；防止 TOCTOU |
| 多写者冲突 | 改动互相覆盖 | 单写者锁；后续使用 worktree/patch 合并 |
| 只靠 prompt 限权 | 角色可能仍执行危险命令 | 精确工具白名单、shell wrapper、容器/OS sandbox |
| stdout 叙述不可靠 | 状态无法自动推进或产生伪造审计 | schema 校验；Phase 0 评估 JSON/RPC tool 事件；失败时状态停在当前阶段 |
| 成本不可见 | 多 agent 工作流难以运营 | 每次委派记录 usage、时长、重试和阶段预算 |

## 10. 分阶段实施建议

### Phase 0: 治理模型验证

- 定义 Policy、Context Capsule、Artifact、`delegate_task` 和 `WorkerResult` schema。
- 用一个只读 investigator worker 和一个只写 implementer worker 做端到端试验。
- 验证 `--no-extensions`、`--no-skills` 加显式 `--skill`、strict/inherited context mode、取消信号、认证继承和 worker cwd。
- 对路径越界、symlink、嵌套 Pi、网络/凭证、Policy/trace 篡改和进程树取消进行失败测试；底层拒绝才算通过，role prompt 不算。
- 对比 `-p`、JSON 和 RPC，确认能记录 tool call、usage、实际 context manifest 与 skill 使用证据。
- 用真实 worker trace 重新执行 architect/challenger/arbiter 评议，检验此设计是否可行。

### Phase 1: 最小可用治理 runtime

- 注册 `delegate_task`、`get_workflow_status`、`get_artifact`。
- 主 agent 只保留 delegate/status/artifact 工具。
- 解释一个版本化 Policy：角色白名单、skill 路由、Context Capsule、产物 schema 和单写者锁。
- 子 Pi CLI worker，记录本地 JSON trace，并将摘要写进 Pi session。
- 支持 `investigator`、`implementer`、`verifier`、`reviewer`，并拒绝不符合阶段、权限或 skill policy 的委派。

### Phase 2: 入口路由和方案协作门禁

- 实现 `build`、`work`、`bug` 三类入口及状态机。
- `build` 固定先需求对齐和方案对齐。
- `work` 先分类，按 `local_change`、`requirement_change`、`design_change` 分流。
- `bug` 先调查，只有调查产物判定为 `design_change` 才进入方案对齐。
- 引入 architect A/B、challenger A/B、arbiter 的阶段状态机。
- 交叉 review、finding disposition 与轮次上限。
- 入口命令映射到状态机启动，而不是仅展开提示词。

### Phase 3: 运行时增强

- 从 CLI stdout 协议迁移到 `--mode rpc` 或 Pi SDK，取得可靠的流式事件和 usage。
- 使用独立 worktree 支持受控并行实现。
- 增加可视化 trace、失败恢复、预算上限和策略配置。

## 11. 需要验证、尚未结论的事项

以下项不能在没有实际运行测试前声称已经成立：

1. 当前 Pi 安装的 CLI worker 能否在不显式传 key 的情况下继承所需认证与模型选择。
2. `pi.exec()` 的 cwd 和环境继承是否符合 worker 预期。
3. `AbortSignal` 是否能完整终止 worker 及其 tool 子进程。
4. `--no-extensions` 与项目 `AGENTS.md` / settings 的实际加载组合。
5. 受限 shell wrapper 或容器是否能有效避免 reviewer/verifier 写入工作区。
6. `-p` stdout 的结构化输出在截断、错误和模型偏离时是否可靠；JSON/RPC 是否能可靠记录 tool event、usage、context manifest 与 skill 使用。
7. 多 agent 角色提示词能否稳定输出 `WorkerResult` schema，还是应使用 custom tool 作为强制收口。
8. `--no-skills` 加显式 `--skill` 是否在当前 Pi 版本中完全满足资源发现白名单预期；strict/inherited context mode 是否能完整捕获 `AGENTS.md`、SYSTEM 和其他加载资源。
9. Policy 文件如何按项目覆盖全局默认策略，以及策略变更如何版本化、审核和回滚。
10. Policy、Artifact 与 trace 能否置于 worker 不可写且按 run 固定 hash 的控制平面，避免 symlink 与 TOCTOU 篡改。
11. 在不可信/高风险项目上，哪种容器或 OS sandbox 能限制 worker 的路径、网络、凭证与嵌套进程。

## 12. 当前建议的决策

先实现 **CLI worker + 有限状态机 + 单写者 + 结构化 trace**，而不是一开始做 in-process SDK 多 session 或同时引入外部 agent-team runtime。

原因不是 CLI 是最终形态，而是它以较小的代码面验证最关键的产品问题：角色拆分是否真正提高方案质量和审查质量，交叉 review 是否能收敛，权限隔离能否成立，证据链是否足够支撑最终结论。上述机制经真实任务验证后，再迁移 SDK/RPC 才有明确收益。
