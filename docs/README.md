# 五层文档总览

本仓库使用五层模型维护产品、实现、项目默认、GitHub 治理和本地工作现场。分类按内容责任，不按篇幅、读者或文件类型；目录用于承载已经确定的责任。

## 层级地图

| 层级 | 回答的问题 | 正式承载 | 真理源状态 |
| --- | --- | --- | --- |
| [第一层 L1](01-产品定义/) | 产品是什么、必须保证什么？ | Core 产品定义、上下文摘要、Extension 产品规范、产品级 ADR | 已采纳文档是产品意图真理源 |
| [第二层 L2](02-产品实现/) | 当前怎样实现、真实实现了什么？ | 实现架构、可执行 Definition、源码和测试 | 源码和测试是当前运行事实真理源 |
| [第三层 L3](03-项目落地/) | 仓库怎样承载、配置、构建和发布产品？ | monorepo、package、目录与项目默认 | 已采纳项目默认是真理源 |
| [第四层 L4](04-仓库治理/) | 如何协作、验证、交付和关闭工作？ | GitHub 流程、Agent 规则、质量门禁 | 共享治理真理源 |
| [第五层 L5](05-本地开发控制/) | 什么只维持当前本地工作现场？ | ignored 本地材料 | 不是正式真理源 |
| [归档](归档/) | 哪些材料只用于研究、比较或历史追溯？ | 历史选型、评审原文 | 不是活跃规则 |

## L1 / L2 判断

```text
L1：产品必须保证什么
L2：Runtime 当前怎样保证，以及实际做到了什么
```

- Feature/Fix 的目标、Stage 语义、必要 Artifact、Guard 条件和 Acceptance 语义属于 L1，由各 Extension 拥有。
- 可执行 Workflow Definition、状态枚举、Transition 配置、Policy 解析、Artifact schema、Guard 代码、Worker 生命周期和测试属于 L2。
- 供 Agent 注入的产品上下文摘要仍是 L1 的派生版本；短并不代表 L2。
- L1 可以领先于实现。L2 尚未满足 L1 时必须显式记录 drift，不能把目标契约写成当前事实。

## Owner 与冲突优先级

1. L1 Core 拥有共享产品语义；Feature/Fix Extension 各自拥有入口特有产品流程。
2. L2 源码和测试拥有当前运行事实；它们不能反向静默改变 L1 产品意图。
3. L1 与 L2 冲突时，记录 drift，并决定修正实现或重新评审产品契约。
4. L3 只定义已采纳的仓库承载方式，不拥有产品流程或 Runtime 机制。
5. L4 约束共享协作和交付；L5 与归档不能覆盖正式层。

## 文档状态

| 状态 | 含义 |
| --- | --- |
| `TODO` | 已识别问题，尚未形成契约 |
| `ALIGNING` | 正在收集事实和方案 |
| `REVIEWING` | 等待独立评审或用户决定 |
| `DECIDED` | 已采纳，可作为下游输入 |
| `IMPLEMENTING` | 已批准并正在实现 |
| `VERIFIED` | 已有对应运行验证证据 |
| `BLOCKED` | 缺少决策、事实或验证，不能继续 |

只有 `DECIDED`、`IMPLEMENTING`、`VERIFIED` 中明确标注为规范性的 L1 内容可以作为产品意图。是否已实现仍必须读取 L2。

## 写回路由

- 共享产品语义或产品级架构边界：写 L1 Core。
- Feature/Fix 特有目标、流程和验收：写对应 L1 Extension。
- 机器上下文摘要：从权威 L1 派生，不独立新增规则。
- 实现机制、源码、测试和当前技术事实：写 L2。
- package、目录、构建、安装或项目默认：写 L3。
- GitHub、Agent、Review、验证和交付规则：写 L4。
- 临时任务状态、trace、handoff、session 草稿：留在 L5 本地。
- 研究、方案比较、外部背景和评审原文：写归档。
