## 现状写作规则

| 规则 | 含义 |
| --- | --- |
| 写完整现状 | 直接说明当前行为、结构和规则，不用“本轮改了什么”代替系统说明 |
| 不混淆契约与实现 | L1 可以有已采纳但尚未实现的保证；L2 必须标明未实现、未启用、未验证及 drift，不把目标写成事实 |
| 不重复维护 | 一个事实只有一个主要 owner；索引和摘要只给定位与链接 |
| 保留必要版本 | 当前协议版本、兼容路径和生效配置属于现状；变更前后对比不属于主文 |
| 分开过程证据 | 评审、变更经过和单次测试结果进入 Issue/PR 或归档；本次任务限制和本机安排留 L5 |
| 按需表达 | 开头结论先行，图表达关系，表比较差异，短段落解释原因；不为了格式复制同一结论 |

详细执行要求由 [AGENTS.md](../AGENTS.md#文档写作只描述现状)拥有。精简不能改变产品契约、降低门禁或掩盖缺口。

## 真理源与写回

| 内容变化 | 唯一 owner 与约束 |
| --- | --- |
| 产品目标、用户行为或共享语义 | L1 对应 Extension / Core；摘要只能从权威定义派生 |
| 实现机制、源码、测试或当前技术事实 | L2；源码和测试是运行事实的权威，机制文档不能重新定义产品语义 |
| package、安装、构建、目录或项目默认 | L3；实验配置采纳前留在 L5 |
| Agent、review、验证或交付规则 | L4；本地备注不能绕过共享门禁 |
| 当前任务和临时现场 | L5；不能直接提升为正式规则 |

一个文件出现两个主要责任时，先拆分责任再写回。L1 与 L2 冲突时明确记录 drift，不能静默改写一方掩盖差异。

## 文档状态

| 状态 | 含义 |
| --- | --- |
| `TODO` / `ALIGNING` / `REVIEWING` | 待明确、对齐或评审；不能作为已采纳契约 |
| `DECIDED` | 已采纳；不表示已实现 |
| `IMPLEMENTING` | 已批准并在实现；具体完成范围看 L2 |
| `VERIFIED` | 标注范围已有对应验证证据；不能扩大到未验证场景 |
| `BLOCKED` | 缺少必要决策、事实或验证，不能继续 |

只有 `DECIDED`、`IMPLEMENTING`、`VERIFIED` 中明确标注为规范性的 L1 内容可作为产品意图；当前运行能力仍以 L2 为准。
