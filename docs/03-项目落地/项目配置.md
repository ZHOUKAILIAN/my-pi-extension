# 项目配置

- 状态：`DECIDED`
- 层级：第三层

本文件说明 GitHub monorepo 的默认配置由谁拥有。配置定义项目如何承载产品，不定义产品本身的长期语义。

| 配置 | 责任 | 修改要求 |
| --- | --- | --- |
| `package.json` | workspace 范围、共享测试和类型检查命令、开发依赖 | package 或脚本变化时同步更新第三层 |
| `package-lock.json` | npm 依赖解析结果 | 依赖变化时由 npm 更新，不手工维护 |
| `packages/*/package.json` | package 名称、入口、依赖和 Pi manifest | 与 package 边界和源码入口保持一致 |
| `tsconfig.json` | TypeScript 编译和类型检查默认值 | 编译边界变化时更新 |
| `.pi/workflow.json` | 可信项目下各 Node 使用的模型和 Skill 选择 | 不得包含 token、凭证或用户数据 |
| 项目 Skill / Project Knowledge | 当前仓库的目录、模块关系、领域术语、调查边界和验证命令 | 不改变 Workflow 状态机；必须能被 Worker 读取并在 Artifact/trace 中引用 |
| `.gitignore` | 生成物、依赖和本地状态的 Git 边界 | 新增本地或生成材料时先判断是否应进入正式层 |

## Workflow 项目配置

`.pi/workflow.json` 是项目共享的 Workflow 执行选择，不是第五层 session 状态。Pi 只在项目受信任时读取它。文件可以选择各 Node 使用的模型和 Skill；模型和 Skill 名称可以进入 Git 历史，但账号凭证、环境密钥和个人数据不得写入该文件。

项目配置不能修改 Workflow 的整体流程、Stage、Node 归属、Transition、Guard、Review 最低门禁、工具能力边界或 Acceptance 最低条件。Skill 可以提供项目特有的调查方法、验证清单、验收证据格式和命令，但不能单独授权流转或宣称 Run 已完成。

Runtime 内置 Workflow Definition 和默认策略；`.pi/workflow.json` 未声明的 Node 使用 Runtime Defaults。当前仓库原有 `.pi/workflow-models.json` 是迁移前的旧配置名，源码尚未切换到 `.pi/workflow.json`，实现迁移时需同步更新 parser、测试和兼容策略。

实验性的模型、Skill 或运行参数在明确采纳前只放本地第五层。采纳后再更新 `.pi/workflow.json` 和对应 L2 测试；只有当产品允许的能力、隔离承诺或行为语义发生变化时，才更新受影响的 L1 owner。

## Workflow 与项目语境

Workflow Runtime 只提供通用的状态、交接、恢复、Guard 和审计机制，不拥有 Feature/Fix 的业务流程，也不假设当前项目一定有前端、后端、数据库或特定外部服务。项目应通过 Skill、Project Knowledge 和项目策略提供这些语境：

- 当前仓库包含哪些模块、调用方和被调用方；
- 某类问题需要沿哪些影响面调查；
- 哪些证据、测试命令和业务不变量才足以形成结论；
- 哪些范围无法访问或尚未验证。

Skill/项目知识负责定义方法和标准，Worker 负责执行并提交结果，Runtime 负责把实际工具事件、Artifact、未验证项、状态迁移和 Guard 决策持久化为可审计记录。不能因为模型加载了 Skill，就把 Skill 中的“应检查”视为已经检查；必须有工具事实或结构化 Artifact 证据。
