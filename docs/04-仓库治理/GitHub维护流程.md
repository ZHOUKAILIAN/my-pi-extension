# GitHub 维护流程

- 状态：`DECIDED`
- 层级：第四层

本项目使用单一 GitHub monorepo 维护。GitHub Issue 和 PR 保存共享工作记录；各层的活跃文档、源码、测试和配置仍是对应责任的正式真理源。

## 开始工作

1. 在 Issue、用户请求或任务说明中确定目标和边界。
2. 按 `docs/README.md` 将内容路由到主要层级；涉及 L1 时继续区分 Core 与具体 Extension owner。
3. 找到已有 owner 文档、源码模块和测试；已有 owner 时不得创建平行真理源。
4. 执行 [AGENTS.md 的产品能力与五层对齐门禁](../../AGENTS.md#产品能力与五层对齐门禁)：确认产品能力、各层 owner、当前事实与差距、关键决策及验收后再实现。未通过时仅继续调查、讨论和文档对齐，不先写代码再补确认。
5. 对齐后的目标尚未实现或未验证时，在 L2 记录 drift；实现中发现新的产品或跨层冲突，暂停受影响改动并重新对齐。

## 分支与变更范围

- 使用与任务对应的分支和 PR；直接维护 `main` 的策略由仓库所有者决定。
- 一个 PR 可以影响多个层，但必须说明每层为何变化以及写回了哪个正式入口。
- 保持变更聚焦，不回退无关用户改动，不夹带生成物或本地 session 状态。

## Review 与验证

所有需要产生 coding diff 的任务都必须由 `implementer` 执行代码改动与自检，再由独立的 `code_reviewer` 评审。该规则覆盖源码、测试、脚本、构建/运行配置和 UI 代码，不按 work、build、Figma/UI 或改动规模区分；纯文档、纯调查和只读评审不适用。实现者自检或测试通过不能替代独立代码评审。Reviewer 检查需求符合度、仓库规范、状态/合同/版本/恢复/审计风险和测试覆盖；P0/P1 或需修复的 P2 由实现者集中修复，再由同一 reviewer 复审，未复审不得标记完成。

涉及新产品能力、跨层产品/技术方案、数据采集、外部服务或发布时，进入实现前至少经过两条独立评审轴，对应 PR 保留两轴结论：

- 产品语义/指标评审：检查目标、合法分支、漏斗、分子/分母、去重、终态、隐私和验收语义；
- 实现/运营评审：检查当前源码事实、事件产生点、失败恢复、外部服务、部署、安全和 E2E。

评审 Agent 只报告 finding，不修改方案。评审材料保留当前事实、目标设计、L1/L2 drift 和未解决分歧，主 Agent 负责合并意见，不能用总结替代独立评审。采纳结论写回活跃 owner；评审原文和过程留在 Issue/PR 或归档，不复制进产品与技术正文。未解决的 P0/P1 finding 或关键产品决策未确认时，不得进入实现。

PR 至少说明：

- 目标和影响范围；
- 受影响的层级与正式 owner；
- L1 与 L2 是否一致；若不一致，drift 是否已明确记录；
- 执行的验证命令及结果；
- 未执行检查、已知缺口和剩余风险。

## Agent 与 CI 的职责

`AGENTS.md` 保留 Agent 的行为责任和规则入口；本流程拥有检查、授权和交付政策，workflow/脚本拥有具体执行步骤，远端分支保护拥有合并约束。自动化执行不改变产品与权限语义。

| 控制面 | 责任 |
| --- | --- |
| Agent | 找到唯一 owner、确认决策与授权、自检、准备完整范围和快照、处理 finding、披露缺口 |
| 基础 CI | 无 AI 凭据地执行完整测试、类型检查及仓库 Markdown 相对链接检查 |
| AI 检查 | 按受信标准独立检查五层一致性与代码正确性；将结构化业务结论转为状态，不以模型进程退出成功代替批准 |
| 合并门禁 | 验证所需检查及 strict up-to-date；远端 required check 不能由本地成功替代 |

### 本地自检与合并证据

- 合并前所有 PR（含纯文档）必须有完整测试与类型检查的通过证据；文档移动或链接变化须检查全部仓库 Markdown 相对链接。当前命令及本地输出控制如下：

```bash
npm run test:agent
npm run typecheck
node scripts/ci/markdown-links.mjs
```

- `test:agent` 与 `npm test` 共用完整范围；参数和日志格式由 [L3 Node 测试摘要](../03-项目落地/项目配置.md#node-测试摘要)拥有。不减少测试范围以压缩输出，不将逐条成功日志灌入上下文。
- 成功后保留机器摘要，不为再次确认而回读完整成功日志；失败先读摘要及必要片段，再定向读取原文。定向测试或排查包装器时同样控制输出，保留真实退出状态，不能用管道末端成功掩盖失败。
- 修复期间先定向验证，冻结候选后再完整验证。同一代码快照、命令、范围、依赖和环境已有有效结果时复用，不仅为展示或送审重复跑全量；条件变化或证据存疑时补查。
- CI 尚未覆盖、不可用或不对应当前候选时，由本地完成适用检查并保留结果。CI 已提供同一待合并快照的完整证据时可复用，须注明 PR head、实际测试的 commit/merge SHA、环境和覆盖范围；Agent 的修改过程自检仍适用。
- 缺环境、失败、取消、关键步骤跳过和路径过滤未运行不能写为通过。修改检查要求、配置凭据或计费、Push/PR、远端设置变更仍须相应明确授权；不自动部署、生产写入或合并。

## 三项交付检查

三项检查分别形成结论，不互相替代：

| 检查 | 判定内容 | 执行证据 |
| --- | --- | --- |
| 代码可用 | 完整测试与类型检查是否通过 | 命令、退出结果、快照、依赖与环境 |
| 五层一致性 | 正式 owner、产品契约、运行事实、项目默认、治理与本地边界是否自洽 | 独立只读 AI 的位置、依据、差异及未覆盖项 |
| Code Review | 正确性、需求符合度、安全、状态/恢复与测试是否存在缺陷 | 独立评审；仍须读取源头规格，不因有五层检查而省略 Spec 轴 |

### 五层一致性标准

检查以完整任务改动为入口，覆盖关联存量调用链和合同，不要求每次修改五层文件，也不无差别审计全仓库。

| 层级 | 核对内容 |
| --- | --- |
| L1 | 实现符合已采纳产品契约；摘要忠于权威定义；未实现要求在 L2 有 drift |
| L2 | 说明符合源码、测试和真实产生点；不把目标、部分接线或离线测试写为已启用、真实 E2E 已验证 |
| L3 | package、依赖、入口、导出、配置、安装方式和宿主兼容范围与实际文件和证据一致 |
| L4 | 角色、评审、验证、交付规则与实际执行一致；规则已采纳不等于自动门禁已部署 |
| L5 | 只核对明确提供的相关本地材料及提交边界；临时配置、session、trace 和未采纳结论不得覆盖正式层，不主动收集无关私有材料 |

工具/角色 `description`、prompt 和提交合同是行为接口，需核对职责、权限、适用条件、输入输出及完成标准，不能只当作润色。归档用于追溯，不恢复为现行规则。

差异按唯一 owner 处理：实现违背契约则修代码；说明落后则在确认产品行为未变后更新对应说明；有意改变产品、默认或治理规则须确认决策后同步；已采纳但未实现/未验证的目标保留并在对应 L2 集中记录缺口；本地实验在明确采纳前留 L5。已报告 drift 不自动等于新缺陷，也不等于允许启用或验收，不通过静默改写 L1 或创建平行真理源掩盖差异。

### 执行、结果与复查

1. 固定原始 SHA、完整功能范围、比较模式及改动归属，包含相关已提交、未提交和新增文件。未提交内容保留实际 diff/文件内容或可核验快照，不能只写 HEAD。
2. 实现者自检后，代码任务先完成代码可用检查，再把同一快照交给相互独立的只读五层检查和 Code Review；可并行执行，检查者不修改文件。
3. 分别输出 `PASSED`、`CHANGES_REQUESTED`、`BLOCKED` 或 `NOT_APPLICABLE`，附范围、依据及未覆盖项。纯文档交付的代码可用与 Code Review 可有理由地不适用，但仍需五层与相关机械检查，不豁免合并前完整测试要求。未执行不算通过。
4. Finding 给出位置、期望与实际、依据、严重度、影响、修正 owner、关闭条件及待用户决策。P0/P1、需修复 P2、关键决策缺失或适用检查阻塞时不得标记完成。
5. 集中修复后保留原始基准和完整范围，由原检查者复查新快照；继承未变化证据前排除间接影响。检查工具不能覆盖约定比较模式或范围时须阻塞，不用空 diff 批准。

## GitHub 云端检查与授权

[基础 CI](../../.github/workflows/ci.yml)针对所有 `main` PR，无 AI 凭据地执行代码可用和链接检查。[AI 工作流](../../.github/workflows/ai-review.yml)从受信 `main` 加载脚本与锁定依赖，只将 PR Git 对象当作数据，不 checkout、安装或执行 PR 中的代码、配置、扩展与 prompt。

- 自动调用仅允许 `ZHOUKAILIAN` 同时作为 PR 作者、事件 actor、rerun triggering actor，且 PR 来自本仓库分支。
- 其他作者或 fork 默认不调用模型、不放行 AI 门禁。所有者可在默认分支通过 `workflow_dispatch` 指定 PR 编号，明确授权评审该快照；触发者及重新运行者都须为所有者。
- 授权与证据绑定 `(repository, head SHA, current main/base SHA)`；用户允许完全相同快照跨 PR 编号复用结果。实现不承诺每次触发都命中缓存，重新运行仍可能消费额度。
- 运行前校验当前 main/base 与祖先关系，过期分支须先更新；最终回写前再次核对 head/base。合并保护须启用 strict up-to-date，不能靠检查发布时的核验替代合并时新鲜度验证。
- 两轴使用独立 Session 顺序运行，固定精确模型 `openai-codex/gpt-6-astra`，同时核对 SDK 请求身份及可观测的实际响应模型，不自动降级。模型仅有受限快照读取/搜索工具；这不是 OS sandbox 的隔离承诺。
- PR 正文须按[模板](../../.github/PULL_REQUEST_TEMPLATE.md)提供原始目标、已确认决定和源头规格。云端读取 PR 及其引用的本仓 Issue 作为不可信需求资料，不把其内容当作系统指令；外部链接不自动抓取，本地对话或外部需求的关键决定须复制到正文。来源缺失、未完整读取或超预算则阻塞；最终发布前复核来源 fingerprint，需求在运行中变化不能沿用旧判定。
- 超预算、无法完整读取、非文本/不支持文件模式、错误模型、异常终止、无效结果合同、未覆盖项和阻断 finding 均不能通过。仅纯 Markdown 变更的 Code Review 可有理由地不适用，五层检查仍须通过。
- 候选结论先写 Step Summary；只有模型结论、工作流步骤、OAuth 回存全部成功且快照仍新鲜时，才向 PR head 发布 `ai-review / result` 成功。基础检查名称为 `ci / tests-and-types`，不得将 `pull_request_target` 默认 base 上的 job 结果冒充 PR head 检查。
- OAuth 使用专用 CI 登录；全局串行与 Environment 启动作业取值避免并发刷新与排队时旧 secret。更新后的凭据需安全回存，不能进入缓存、artifact 或日志。作业被强杀或回存失败可能需要人工重新登录并播种，失败不放行。

### 部署与启用条件

工作流与脚本已定义；专用凭据、真实云端模型调用、外部 PR 手动授权、OAuth 续期/回存和旧状态随 base 变化失效的 GitHub 验收尚未完成。配置方法见 [L3 云端 AI 检查](../03-项目落地/项目配置.md#云端-ai-检查)。

首次接入时，`pull_request_target` 和默认分支 dispatch 需要工作流已存在于 `main`；不能把 bootstrap PR 未运行 AI 写为通过。先完成独立本地评审和基础 CI，再由用户明确合入；随后配置凭据、完成真实试跑，最后才将正确来源的检查设为 `main` 必需项并验证 strict up-to-date 和取消/失败场景。不自动合并 bootstrap，也不先配置缺少执行来源的必需检查锁死仓库。

涉及真实 provider、Pi UI 或外部运行环境的行为，仅有单元测试时不得声称 E2E 已完成。

执行中 Worker 协作能力合并前还必须验证：

| 验证项 | 最低证据 |
| --- | --- |
| 单一输入路由 | streaming/idle 输入都到提交时绑定的 Worker；Node close fence 前输入使旧 Artifact 失效并触发绑定最新补充版本的重新交付，fence 后提交保留内容且不广播、不静默改投；真实 ExtensionRunner 吞异常时 input 仍返回 handled、before lifecycle 仍返回 cancel |
| 上下文连续 | recorded/enqueue_accepted/model_call_completed/artifact_bound 逐条可核对；同一 Run 后续 Capsule 使用连续 supplementVersion，恢复后无跳过 |
| 模型切换 | 选择器目标变化 fail-closed；候选满足 scoped/认证/兼容约束；已请求/待生效/已切换/未应用/失败与 Child AgentSession、Audit 一致且不误改主 Session |
| 控制边界 | 补充信息和模型变化不能扩大 tools/skills/capability，不能绕过 Artifact、Guard 或 Acceptance |
| 恢复 | 在 Run Control WAL append/fsync、enqueue、模型调用、Artifact、checkpoint 各边界做崩溃故障注入；operation lock + writer lease/epoch覆盖双 Pi进程、核验/append竞态、reload旧callback迟到和stale owner接管；compaction/sibling branch不作为控制事实；同 Node恢复重投明确展示，跨 Node不自动改投；legacy导入幂等且失败不双写 |
| 父 Session 生命周期 | `/tree`、switch/fork/new/resume、重复 `/fix` 对可取消接缝 fail-closed；reload/shutdown 不虚假承诺可阻止退出，缺少终态时从 durable WAL 推断 interrupted；旧 branch 不再收输入，父 Session 首次落盘前崩溃可经用户确认重绑 |
| 本地数据 | 受控目录实际为 `0700`、文件为 `0600`；20 attempts上限、settled intermediate 30 天、无 live lease unfinished 30 天、parent缺失 settled最多7天可验证；GC锁内复核、tombstone/rename和删除重试覆盖与恢复竞态；新 Run export/share只含 opaque ID/粗状态，legacy边界有提示，公开 Trace/Telemetry无原文 |
| 宿主兼容 | lockfile Pi 版本与受支持宿主均验证；Child 独立 SettingsManager、input hook、后台任务、自定义 editor/keybinding、picker 和 session API 有契约测试，接缝缺失时 fail-closed |
| 真实交互 | 至少一次真实 Pi TUI + provider E2E，证明 `/fix` 单一入口、同一输入框补充和 Child 专用模型选择；单元测试不能替代 |

## 文档写回

活跃文档只描述现状，具体写作要求见 [AGENTS.md](../../AGENTS.md#文档写作只描述现状)。每次写回直接维护 owner 的完整规则或实现说明，不追加“本轮修改”日记，不另建并行简版。尚未实现、未启用、未验证和 drift 必须保留，精简不降低产品契约或质量门禁。

| 材料 | 保存位置 |
| --- | --- |
| 当前产品保证、机制、默认配置与共享规则 | 对应 L1–L4 owner |
| 变更经过、独立评审原文、固定 revision 的验证结果 | Issue/PR 或归档；活跃正文只链接必要证据，不复制单次通过数 |
| 当前任务限制、进度、handoff、个人部署安排 | L5 ignored 本地材料，不提升为共享规则 |

- Bug、回归和已有能力优化：产品契约不变时只更新 L2 实现与测试；契约变化时更新对应 L1 owner，并同步实现或记录 drift。
- 新能力：在对应 L1 Extension 建立或补齐产品规范，再实现 L2。
- 纯重构：更新 L2；明确 L1 行为未变。
- L1 产品上下文摘要只能从权威定义派生，不得成为第二套规则源。
- package、配置或目录：更新第三层。
- 协作或质量规则：更新第四层和必要的 `AGENTS.md`。
- 调查、方案比较和评审原文：进入归档，并从已采纳层链接到结论的正式写回位置。

## Extension 清单与仓库简介

新增 Extension 时，同步更新根 README 的扩展清单和 GitHub 仓库 About 的 `description`；移除或调整主要能力时也应保持两者准确。简介以简短项目定位和主要 Extension 为主，不将待实现能力描述为已可用，不把普通 library 列为自动加载的 Extension。

远端简介在发布授权范围内更新并读回核对；尚未执行时列为未同步项，不把本地文案修改当作 GitHub 已更新。

## 完成与合并

只有以下条件满足时才可以声称任务完成：

1. 所有受影响层都有明确 owner 和必要写回。
2. 未报告的产品定义与实现漂移为零。
3. 自动验证已通过，或阻塞已明确说明。
4. Markdown 内部链接在文档变更后仍可解析。
5. Git diff 中没有 secrets、生成物、临时 trace 或无关改动。
6. 新增 Extension 的根 README 清单与仓库 description 已同步，或远端更新的授权/执行缺口已明确。
