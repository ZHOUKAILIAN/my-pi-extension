# 第四层：仓库治理

第四层回答“如何在 GitHub 上协作、验证、交付和关闭工作”。它管理共享执行方式，不定义产品语义，也不替代源码和测试。

## 正式入口

- [GitHub 维护流程](GitHub维护流程.md)
- 根目录 [`AGENTS.md`](../../AGENTS.md)：Agent 可发现的执行规则

## 当前门禁

- 修改前先完成五层路由并找到唯一 owner；L1 同时区分 Core 与 Extension owner。按任务读取相关文档，不要求逐层通读。
- 活跃正文描述完整现状，不承载变更经过或本轮任务安排；[现状写作规则](../../AGENTS.md#文档写作只描述现状)由 `AGENTS.md` 拥有，证据保存位置见 [GitHub 维护流程](GitHub维护流程.md#文档写回)。
- 产品行为变化先更新 L1；L2 同步实现，或明确记录尚未实现的 drift。
- 纯实现修复或重构若不改变产品契约，只更新 L2 和验证证据。
- package、目录、构建或项目默认变化必须同步第三层。
- 代码可用、五层一致性和 Code Review 分别给出结论，见 [三项交付检查](GitHub维护流程.md#三项交付检查)。
- Agent 自检、CI 执行与合并约束分开维护，见 [执行分工](GitHub维护流程.md#agent-与-ci-的职责)；自动/手动 AI 授权及启用条件见 [云端检查](GitHub维护流程.md#github-云端检查与授权)。
- 第五层临时状态和归档材料不得被当作正式执行规则。
